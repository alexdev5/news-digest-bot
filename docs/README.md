## Як читати вимоги

Початкове ТЗ — v4.0 від 2026-11-10, конфігураційна схема в ньому — 3.
Власник **2026-11-11** уточнив два правила:

1. Включати **всі унікальні новини**, а не лише головні.
2. За перевищення довжини публікувати **кілька послідовних повідомлень із нумерацією частин**.

Ці рішення мають пріоритет над `selection_mode=important`, лімітами 8/6,
вимогою одного Telegram-повідомлення і відповідними UNIQUE-обмеженнями v4.
Решта вимог оригіналу залишається чинною, якщо тут не описано конкретної зміни.

Додаткове уточнення власника 2026-11-11: модель групує новини за змістом,
включно з різними текстами про одну подію, і формує короткий огляд. Публікацію
її перевіреного результату технічно виконує сервіс. Див. D-009.

Того ж дня власник ухвалив D-010–D-021: без реєстру прав, без статусних постів
і видимих маркерів, посилання на найраніший допис групи, хронологічний порядок,
`scan_start_at`, сайти як джерела, JSON-конфіг із `target_channels`. Ці рішення
мають пріоритет над відповідними місцями v4 і описані в [specification.md](specification.md).

Актуальні прямі вказівки власника мають найвищий пріоритет. Усередині документації:
підтверджені рішення → `specification.md` → оригінал v4. Рекомендації в огляді
не стають підтвердженими продуктовими вимогами самі собою.

Технічна деталізація серій у `architecture.md` — робочий контракт для реалізації
підтвердженого формату. Невідомі дані для production явно перелічені в `decisions.md`.
Не вимагати їх для початку офлайн-розробки.
