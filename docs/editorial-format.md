# Стислий виклад, підподії та цитати

2026-11-12, рішення власника D-034–D-036. Реалізація: `group-v6`,
`ai/editorial.py`, `ai/grouping.py`, `pipeline/events.py`, `pipeline/render.py`.

## Формат для читача

- Коротка новина: `N. 📰 Один стислий абзац із суттю. — Джерело`.
  Окремого заголовка, який повторює цей абзац, немає.
- Довша новина: жирний короткий заголовок, під ним лише додаткові факти.
- Довга новина з кількома думками (D-040) і пов'язані підподії: заголовок —
  головна думка, кожна логічна думка коротко з нового рядка через `▪️`.
  Загальної «портянки» й повторного викладу цього списку немає.
- Один влучний коментар або питання з оригіналу можна залишити окремим рядком
  у `«»`, без «Автор допису іронізує», «Коментар автора» тощо. Модель не вигадує
  коментарів; це точний суцільний уривок джерела, у його мові, зі збереженням питання.
  Цитата необов'язкова; важливі факти мають пріоритет.

Умовний приклад (синтетичні дані):

> 1. 📚 **У селищі відкрили бібліотеку**
>
> ▪️ Вона доступна школярам і дорослим.
> ▪️ Читальний зал відкриють наступного тижня.
>
> «А хто поверне книжки?»
>
> — Джерело

Видиме посилання лишається одним: найраніший учасник групи (D-015). Джерело
цитати перевіряється окремо й може бути іншим учасником; його ID зберігається
в metadata опублікованого пункту. Окремих підписів перед цитатою немає.

## Що перевіряє код (D-036)

Редакторські правила — мета для моделі, а не умова публікації випуску.

**Виправляє код сам, без повторного запиту:** зовнішні лапки й вступ на кшталт
«Автор допису іронізує:» у цитаті; цитата порівнюється з джерелом без урахування
типографських лапок, апострофів, тире й пробілів; цитата, якої в джерелах події
немає, прибирається (новина лишається); `quote_candidate_id` виставляється на
допис, де цитата справді є; список з одного пункту стає summary; compact із
summary/bullets стає detailed; маркери `▪️`/`•`, а `-`/`2.` лише з пробілом після
них, прибираються з bullet (`-5 градусів` і `1.5 млн` не змінюються);
порожній title за наявного summary — summary стає title; задовге emoji прибирається.

**Зміст — одна спроба моделі виправити, далі публікація з лічильником `ai_warning_*`:**

- `numbers` — числа чернетки немає в джерелах у жодному рівнозначному записі.
  Рівнозначні: `1 млн` = `1 000 000` = `1000000`, `1,5 млн` = `1500000`,
  `2 тис.` = `2000`. Множник — частина значення: `1 млн` ≠ `1 млрд` ≠ `1 грн`.
  Окремі складники дозволені лише з дат і часу джерела (`11.11.2025`, `15:30`);
  час публікації кандидата — як `HH:MM`.
- `length` — редакторський текст (title, summary, bullets, quote) довший за
  оригінал: найдовший очищений допис події, для підподій — сума найдовших на
  кожну підподію без повторів. «Оновлення:» не рахується. Цілі ~85/65/45 % — у промпті.
- `attribution` — «за даними/як пише <назва каналу-джерела>» (D-030).

**Підбірки (D-037):** один допис може бути в кількох різних пунктах; заборонено
лише бути водночас у пункті й у виключеннях або виключеним двічі. Якщо одну
новину підбірки прийнято, а іншу треба виправити, допис лишається в обробці з
`already_accepted` (заголовки вже прийнятих), щоб модель їх не повторила.
Злиття дублікатів отримує `merge_drafts` і має повернути рівно одну подію;
інакше лишаються перевірені чернетки. Допис стає використаним (source ID у БД)
лише з частиною серії, де стоїть остання з його новин.

**Блокує лише окремий пункт (повтор):** невідомі candidate_id, конфлікт пункт/виключення,
пункт без candidate_ids або без тексту. Виключити новину замість виправлення не можна.

Публікуємо лише текст (D-038): допис без тексту, зокрема мем-картинка, моделі не
передається. Модель бачить лише позначку `has_photo`: короткий жарт/мем, суть
якого в картинці, виключається як `not_news` (D-042). Пункт передає зміст, а не
описує допис: без «Допис про», «Жарт про» (D-041). Допис із необробленим залишком не записується використаним.

Після трьох спроб невраховані кандидати повторюються окремими запитами по одному
(до двох спроб). Кандидат, якого модель уже подавала як новину, і в цьому
повторі не можна виключити. Що не вдалося — `ai_unprocessed`, випуск виходить без них.
Весь випуск зупиняється лише коли пачка не дала жодної придатної відповіді або
впав API (D-011).

Абсолютних лімітів символів на пункт чи цитату немає. Пункт, довший за
повідомлення, продовжується в наступній частині серії: розріз між абзацами,
потім рядками, реченнями, словами; заголовок і посилання не розрізаються, якщо є
інший варіант. Metadata пункту (пам'ять AI, використані source ID) записується
лише в **останню** його частину: поки вона не підтверджена, пункт не вважається
опублікованим.

## Контракт моделі та зберігання

Structured Output доповнений `layout` (`compact` / `detailed`), `bullets`
(`text`, `candidate_ids`), `quote` і `quote_candidate_id`.
У compact весь текст міститься у title; summary і bullets порожні.
Лапки й маркери додає renderer.

Дублікати між пачками й після повторів шукає окремий запит (`DEDUPE_INSTRUCTIONS`):
модель бачить лише короткі чернетки й повертає групи їхніх ID. Код переписує з
**оригінальних дописів** тільки ці групи (`same_event_hint`, виключення заборонені).
Якщо переписування не вдалося — лишаються вже перевірені чернетки. Решта пунктів
повторно не переписується, тож деталі не губляться.

Нові metadata — у наявному JSON `items`; міграції БД не потрібно. `short_summary`
включає підподії для пам'яті наступного випуску, але не редакторську цитату.
Джерельні тексти не додаються до БД або `/state`. Збережені плани доставки
попередніх версій читаються й доставляються без переформатування.

Перевірки — [testing.md](testing.md). Офлайн-тести використовують синтетичні
джерела. 2026-11-12 фінальний AI-merge перевірено на реальних кешованих даних;
це не незалежний аудит усіх семантичних рішень моделі.

## Діагностика AI-збою (2026-11-12)

До D-036 `incomplete_coverage` означав, що після повторів лишилися не враховані
або непридатні кандидати. Сам код не визначає, чи це довжина, число, цитата або
пропущений ID. Раніше ці причини губилися; старий запуск без trace неможливо
точно відтворити лише за цим кодом помилки.

Тепер кожен AI-виклик записує instructions/payload/response, usage і результати
перевірки у `ai/0001.json`, `0002.json`, … всередині тимчасового кешу run.
Помилка має `ai/failure.json` із деталями, які показують `run-window`, `run-now`
та `status --details`. Контентні trace-файли не потрапляють у `/state`, БД чи
звичайні логи; очищаються разом із кешем після успіху або за його TTL.
Невдалий запис діагностики не змінює правила доставки.

Перевірка на даних проблемного запуску виявила два дефекти реалізації:
втрата бази кількох підподій у фінальному merge та хибне відхилення часу
публікації, переданого моделі в metadata. Обидва виправлено в `group-v5.1`.
Валідатор дозволяє точний `HH:MM` із часу відповідного кандидата в timezone
каналу; це не дозволяє використовувати годину/хвилину як довільну кількість.
Промпт розрізняє час публікації й час самої події.
