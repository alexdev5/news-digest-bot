# Ручний випуск за довільний період

`run-window` виконує **сканування → AI → публікацію в канал** за явним періодом.
Це окрема команда від `run-now`, який обирає завершений інтервал розкладу.
Для перегляду без публікації лишається `preview`.

## Локально

Windows, із кореня проєкту:

```powershell
.\run.cmd run-window --channel news_digest_ua --from "2026-11-11T15:00:00+02:00" --to "2026-11-11T21:00:00+02:00" --ignore-published
```

Для локального Linux/macOS замінити `.\run.cmd` на `./run.sh`.
Обгортки запускають команду в Docker з робочим `config/config.json`.

## На сервері

Після деплою нового коду, із `/srv/news-digest`, при запущеному worker:

```bash
docker compose -f docker-compose.prod.yml --profile worker exec -T app \
  digest run-window --config /config/config.json --channel news_digest_ua \
  --from "2026-11-11T15:00:00+02:00" --to "2026-11-11T21:00:00+02:00" \
  --ignore-published
```

Якщо worker зупинений, замінити `exec -T app` на `run --rm app` — команда виконає
прогін сама. За зайнятої сесії команда передає запит чинному worker через
`/state/requests/`, не відкриваючи другу Telegram-сесію. Запит обробляється на
наступному проході циклу після поточної роботи; у вільному циклі — до ~30 секунд.
Код і образ worker мають бути оновлені разом; старий worker новий формат не підтримує.

Результат і ID запиту:

```bash
docker compose -f docker-compose.prod.yml --profile worker exec -T app \
  digest status --config /config/config.json --details
```

Локально — `.\run.cmd status --details`.

## Межі та повтори

- Період `[from,to)`: початок включно, кінець не включно. Обидві дати — ISO 8601
  з UTC offset (`+02:00`, `+03:00` або `Z`). Порожній/зворотний період, кінець у
  майбутньому й початок раніше `scan_start_at` відхиляються до читання Telegram.
- Період не прив'язаний до schedule і не обрізається кінцем останньої публікації.
  Це дозволяє зібрати пропущені новини старого вікна.
- **Без `--ignore-published`**: дописи, вже використані в цьому цільовому каналі,
  пропускаються за ID; модель отримує пам'ять за 24 години. Якщо історію з БД
  прочитати неможливо, run завершується `published_history_unavailable` без AI/публікації.
- **З `--ignore-published`**: використані ID не відсіюються і пам'ять попередніх
  випусків не передається моделі. Новини можуть бути опубліковані повторно.
  Групування дублікатів усередині нового випуску, фільтри джерел та відсів реклами чинні.
- Кожна нова команда створює окремий запит і план. Старі Telegram-повідомлення
  не редагуються/видаляються. Restart або повторна доставка того самого запиту
  зберігають його ключі й random IDs; прапорець не обходить guards і reconciliation.
- Незавершена попередня серія блокує відправку нового ручного випуску. Історичні
  новини з явного запиту можуть виходити після новіших уже завершених випусків.
- Довільний ручний період не зсуває планову межу покриття, щоб не утворювати
  прогалин у наступному автоматичному скані. Його опубліковані ID та власні пункти
  надалі враховуються стандартною дедуплікацією.

Реалізація D-033: ручний `digest_key` має окремий префікс `manual` і hash вікна,
каналу та ID запиту. У БД це ті самі confirmed-only рядки; міграція не потрібна.
Запити не перезаписують один одного та видаляються після обробки; незавершений
scan відновлюється в межах чинного grace, доставка — із незмінного плану до TTL.

Перевірено офлайн в Linux Docker: прямий CLI, зайнятий process lock/черга worker,
повторне включення ID і порожня AI-пам'ять, restart/DB retry, блокування доставки,
валідація часу, збереження планових вікон і PostgreSQL-історії. Живий запуск цієї
команди та деплой у межах реалізації не виконувалися.
