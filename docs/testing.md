# Перевірки й приймання

Це план тестування. Стан на 2026-11-11: офлайн test suite етапів 1–3 —
180 тестів (`tests/unit` + 22 тести PostgreSQL у `tests/integration`), усі проходять
у Docker. Покрито: T01–T16, T20–T22, T28, T32, T35–T38, T41, T45–T46, T74–T76
(у межах реалізованого), M03–M07, M20–M22, M24–M27, схема БД частин і міграція, CLI. Telegram — fake-gateway (`tests/fakes.py`);
живих викликів Telegram у тестах немає. Решта T/M-сценаріїв ще не реалізована.

Команди перевірок:

```powershell
.\run.cmd check      # ruff check + format --check + mypy + pytest у Docker
.\run.cmd test -k dst
```

На Linux/macOS — `./run.sh check`. Ті самі перевірки з PostgreSQL виконує job `check`
у `.github/workflows/deploy.yml` перед кожним автодеплоєм.

Без Docker: `uv run pytest`, `uv run mypy src tests`,
`uv run ruff check src tests`, `uv run ruff format --check src tests`.

## Нові сценарії M01–M20

| ID | Очікувана поведінка |
| --- | --- |
| M01 | 20 придатних унікальних подій з'являються всі; старі ліміти 8/6 не діють |
| M02 | Дублікати з різних AI-пачок і майбутніх частин дають один пункт; refs не губляться |
| M03 | Кожна прийнята подія є рівно в одній частині; пропуск/дубль під час packing виявляється |
| M04 | Поділ тільки між цілими пунктами; один наддовгий пункт дає safe shortening або явний review |
| M05 | N стабільне після додавання headers і `i/N`, зокрема для 9→10 частин |
| M06 | Emoji, ZWJ, combining marks і кирилиця не ламають UTF-16 offsets або межі частин |
| M07 | Кожна частина має `i/N`, унікальний part key/random ID; видимого маркера немає; пункти нумеруються наскрізно |
| M08 | Crash після commit частини 2/5 продовжує з 3/5, без повторів 1/5 і 2/5 |
| M09 | Втрачений ack 2/5 блокує 3/5; reconciliation 2/5 відновлює рівно один confirmed row |
| M10 | DB failure після ack не дає нового send; повторний insert ідемпотентний |
| M11 | Кеш не очищається після першої частини; очищається після всієї серії/shared refs або TTL |
| M12 | Кеш втрачено після часткової доставки: немає регенерації решти з іншим N/текстом; hold |
| M13 | Published-memory містить пункти committed частин, не unsent; partial metadata явно degraded |
| M14 | `preview` очищається; `prepare` зберігає до TTL; `publish` не створює другий payload |
| M15 | Scheduled preview після restart не виконується вдруге через відсутність publication rows |
| M16 | Неповний scan публікує прочитане без позначки в пості, але в `/state` coverage лишається `partial`, не `complete` |
| M17 | Прострочена price table/unknown usage і rollover бюджету не дають безкоштовного «0 USD» резерву |
| M18 | Вимкнення джерела, reload цільового каналу або новіший слот не переформатовують уже розпочату серію |
| M19 | Різні тексти про ту саму подію дають один пункт; додатковий факт/атрибуція другого джерела збережені |
| M20 | Схожі тексти про інший час/місце або зі зміненим числом/запереченням не відкидаються локально як дублікати |
| M21 | Група з дописами B 10:05, A 10:20, C 10:01 → посилання на C; рівний час → вище у списку; сайт може бути найранішим |
| M22 | Пункти йдуть за зростанням часу найновішого допису групи; найновіший внизу; рівний час стабільний |
| M23 | Звірка: рівно один власний пост в інтервалі → confirmed; нуль або два → uncertain; чужий пост не рахується |
| M24 | Нуль придатних новин → жодного send, guard чи рядка БД; у `/state` результат `empty` |
| M25 | Допис, ID якого вже є в `source_message_ids` цього цільового каналу, не потрапляє в новий випуск; в іншому каналі — може |
| M26 | `scan_start_at` обрізає вікно знизу; межі до нього не створюють випусків |
| M27 | JSON-конфіг: дублікати ключів, невідомі поля, змішаний trigger, цільовий канал як джерело → помилка валідації |
| M28 | Сайт: RSS і селектори дають статті тільки з `[start,end)`; стаття без дати виключається; redirect на інший домен/приватний IP блокується |
| M29 | Між вікнами немає HTTP-запитів до сайтів і getHistory до Telegram-джерел |

## Рівні перевірок

- **Unit:** windows/DST/config merge, source order, normalization/dedup,
  validators, packing/Unicode, бюджети й transitions; керований clock.
- **Integration офлайн:** локальний PostgreSQL (тимчасова база на сесію тестів),
  тимчасові директорії, locks,
  atomic writes, mock Telegram/OpenAI/HTTP, синтетичні RSS/HTML fixtures,
  backup/restore, network-call recorder.
- **Fault injection:** падіння до/після durable writes, send, receipt, commit,
  між частинами; cache loss, full disk, corrupted state, stale backup.
- **Зовнішні інтеграційні:** явний запуск із бюджетом у тестових каналах
  власника; фіксується точна версія SDK, моделі й конфігурації.
- **Quality evaluation:** дозволений або синтетичний корпус; фактичні новини
  й секрети не перетворюються на committed fixtures.

Поведінку «немає ingestion» перевіряти записом фактичних source-history
викликів між due-runs, під час startup/healthcheck/doctor, а не лише відсутністю
імені `NewMessage` в коді. Reconciliation own channel розрізняти зі source scan.

## Приймання якості й продуктивності

Початковий корпус v4: ≥200 повідомлень, ≥50 розмічених подій. До числового
приймання визначити парну або кластерну merge-метрику, еталон новизни/оновлень,
event coverage і допустимі exclusions. Цілі merge precision ≥95%, recall ≥85%
з v4 залишаються початковими; без методики це не виконаний критерій.

Для D-001 додатково оцінювати false exclusions і втрати між AI/pipeline/renderer.
Повне покриття вже валідованих подій у плані частин має бути 100%; це **не**
означає обіцянки 100% семантичного recall моделі на довільних майбутніх новинах.
Імена/числа/заперечення перевіряються також людиною на еталонному корпусі.

Вимірювати due scheduling delay, scan/AI time, cutoff→first-part і
cutoff→last-confirmed-part, кількість частин, coverage і реальні costs.
Робочий обсяг (D-018): ~50 вхідних дописів на добу на цільовий канал, ~20 унікальних;
кілька цільових каналів з одночасними межами. Сценарій v4 на 10 000 постів/добу
не є ціллю MVP. Ціль 180 секунд від cutoff — орієнтир, не гарантія.

## Оновлене функціональне приймання

1. Усі придатні унікальні події представлені в серії, без top-N обрізання.
2. Кожна частина вкладається в ліміти й має коректні джерельні entities.
3. Частина потрапляє в БД тільки після підтвердження саме її Telegram message ID.
4. Restart/retry не повторює підтверджені частини; uncertain вимагає звірки.
5. Немає raw-архіву в БД, `/state`, session, logs, backups або image.
6. Виконані A01–A16 v4 з урахуванням D-010–D-021: A03/A14 — для одного логічного
   випуску з N частин; A09/A10 — посилання на найраніший допис групи; A16 охоплює
   актуалізовані T-тести та M01–M29.
7. Є звіт фактично виконаних перевірок, обмежень і 7-денного стендового прогону.
