# Рішення та відкриті питання

Дата: 2026-11-11. Джерело D-001/D-002 — прямі відповіді власника в цьому чаті.
Решта базових вимог перенесена з наданого ТЗ v4; числові defaults не є новими
побажаннями власника.

## Підтверджено

| ID | Рішення | Наслідок |
| --- | --- | --- |
| D-001 | Усі унікальні новини | `selection_mode=all_unique`; немає відбору top-8/top-6 або вилучення через низьку важливість |
| D-002 | Довгий випуск — послідовні частини з нумерацією | Один логічний випуск може мати N Telegram-повідомлень; доставка й БД ведуться для кожної частини |

| D-004 | Читання лише на межі незалежного розкладу профілю | Без постійного збору, startup backfill та сканування всіх підписок |

## Технічні defaults і деталізація

- Python 3.13, один worker, Telethon, SQLite, JSON/JSONL, Docker Compose.
- Інструменти: uv/uv.lock, Typer, pytest/pytest-asyncio, Ruff, mypy;
  asyncio/zoneinfo scheduler, стандартний logging у JSON. Повна таблиця —
  [technology-stack.md](technology-stack.md). Це технічні defaults, не додаткові побажання власника.
- `Europe/Kyiv`, шаблон 08:00/21:00; розклади кожного профілю незалежні.
- Кеш: до завершення обробки, максимум 24 години від створення run; 512 MB;
  переживає restart, не входить у backup.
- Власні публікації: 365 днів; пам'ять повторів: 7 днів; backup: 7 днів.
- `max_chars_per_message=3500`, 1–2 речення на подію, нумерація пунктів наскрізна.
- Частини готуються до першого send; кожна має власні `part_key` і `random_id`.
  За часткової доставки підтверджені частини залишаються опублікованими.
- Чистий `preview` одразу очищає кеш; окремий `prepare` зберігає готову серію
  до TTL для подальшого `publish --run-id`. Це усуває суперечність v4 §8/§22.
- Перехід конфігурації до проєктної schema 4 явно відображає нові поля серій.
  Жодного готового мігратора або чинної конфігурації schema 4 ще немає.

Ці пункти не блокують створення модулів і синтетичних тестів.

| ID | Дані або вибір | Поточний стан |
| --- | --- | --- |
| O-001 | Реальні source refs, їхній порядок, destinations, account/peer IDs | Не надані; демонстраційні значення не підставляти як робочі |
| O-002 | Остаточні години кожного профілю | 08:00/21:00 — шаблон; crypto 09:00/15:00/23:00 — демонстрація |
| O-003 | Бюджет на випуск, день і розрахунковий період | Не заданий; наявність Pro 100 не підтверджує активний API-баланс |
| O-004 | Докази й scope дозволів джерел | Реєстр поки не заповнений; не робити автоматичного `approved` |

| O-007 | SLO довгої серії та робота оператора з незавершеною серією | Потрібні виміри й допустимий строк ручного розв'язання; мовчазного обрізання або rollback немає |

перетворювати на неявні квоти зовнішніх API або гарантії якості.
