# Рішення та відкриті питання

Створено: 2026-11-11. D-001/D-002, D-009 і D-010–D-021 — прямі відповіді власника
в чаті 2026-11-11. Решта базових вимог перенесена з наданого ТЗ v4; числові
defaults не є новими побажаннями власника. Стислий контекст розмов і поточний
стан робіт — у [context.md](context.md).

Термін: **цільовий канал** — елемент `target_channels` у конфігурації, тобто
власний Telegram-канал публікації з усіма своїми джерелами й правилами.
У ТЗ v4 і частині документів це саме поняття називалося «профіль».

## Підтверджено

| ID | Рішення | Наслідок |
| --- | --- | --- |
| D-001 | Усі унікальні новини | `selection_mode=all_unique`; немає відбору top-8/top-6 або вилучення через низьку важливість |
| D-002 | Довгий випуск — послідовні частини з нумерацією | Один логічний випуск може мати N Telegram-повідомлень; доставка й БД ведуться для кожної частини |
| D-003 | Один звичайний акаунт читає й публікує | Початкове припущення асистента про окремого bot-публікатора замінене вимогою v4 |
| D-004 | Читання лише на межі незалежного розкладу цільового каналу | Без постійного збору, startup backfill та сканування всіх підписок |
| D-005 | Кеш тимчасовий; контентна БД лише для опублікованого | Тексти джерел і чернетки не зберігаються в контентній БД |
| D-006 | ~~Видиме посилання за порядком `source_ids`~~ | **Замінено D-015.** Одне видиме посилання на пункт лишається чинним |
| D-007 | OpenAI Responses API / `gpt-5.6-sol` | Модель зберігається без прихованої заміни |
| D-008 | Фіксовані вікна між плановими межами | Рекомендацію асистента про розширення вікна від останнього успіху замінено правилом v4 §7/§15 |
| D-009 | Модель визначає однакові події за змістом, навіть якщо тексти відрізняються | Зібрані тексти передаються в AI-прохід; групування й короткий огляд робить модель, перевірку та відправку — сервіс |
| D-010 | Публічні канали, на які підписаний акаунт, можна читати, обробляти AI й стисло публікувати у власний канал (аудиторія — сам власник) | Реєстр прав v4 (`evidence_ref`, scope, `expires_at`, `allowed_ai_providers`, `pending_review`) не потрібен. Лишається перемикач `enabled` джерела. Ризик щодо умов Telegram для AI-обробки власник свідомо прийняв |
| D-011 | AI — тільки `gpt-5.6-sol` через API; ключ у власника є | Обов'язкової rule_based гілки в MVP немає. Збій AI → випуск не публікується, технічне сповіщення, bounded retry у межах вікна/grace |
| D-012 | Немає новин за вікно → нічого не публікуємо | Статусні пости (`publish_status`, «новин немає») скасовані. Джерельний допис, ID якого вже є серед `source_message_ids` опублікованих частин цього цільового каналу, повторно не використовується |
| D-013 | Дата старту сканування в конфігу | Поле `scan_start_at` цільового каналу; раніше нього нічого не читаємо. Вікно обрізається знизу: `[max(попередня межа, scan_start_at), межа)` |
| D-014 | Видима лише назва джерела як посилання | Видимий marker/hashtag скасовано. Payload hash, digest/part keys — тільки в БД і `/state`. У БД поле `source_message_ids` — масив ID джерельних дописів/статей, використаних у частині |
| D-015 | Посилання групи — на джерело, де новина з'явилася найраніше | Серед придатних учасників події обирається допис із найменшим часом публікації; посилання на цей конкретний допис/статтю. Рівний час → вище в списку (`source_channels`, потім `source_sites`). Замінює D-006 і правило `source_ids` v4 §6/§13.2 |
| D-016 | Хронологічний порядок, найновіші внизу | Пункти сортуються за зростанням часу **найновішого** допису групи; рівний час → стабільний tie-break. Важливість на порядок не впливає |
| D-017 | Звірка невизначеної відправки — за часом публікації та цільовим каналом | Текст не порівнюється. У цільовому каналі шукаємо власний пост в очікуваному часовому інтервалі після `sending`. Не рівно один кандидат → `uncertain`, ручне рішення |
| D-018 | Обсяг: до ~50 вхідних дописів на добу, ~20 унікальних | Поділ на частини лишається запобіжником, зазвичай N=1. Навантажувальні сценарії v4 (10 000 постів/добу) не є ціллю MVP |
| D-019 | Публікуємо те, що вдалося прочитати; непрочитане пропускаємо | Без позначки неповноти в пості; неповнота фіксується лише в технічному журналі/`/state`. Порожній результат через збій ≠ «новин немає», але теж нічого не публікується |
| D-020 | Сайти як джерела новин | Тип `source_sites`: RSS/Atom або сторінка-список + селектори; статті очищаються до тексту й ідуть у той самий AI-прохід. Скасовує заборону веб-завантаження v4 §9/§20/§27; SSRF-захист v4 §20 лишається |
| D-021 | Конфігурація в JSON; верхній ключ `target_channels` | Кожен елемент — власний канал публікації: `id`, назва, опис, Telegram-ref, розклад, `scan_start_at`, джерела, AI-налаштування, фільтри, формат, бюджет. Надалі можливий перенос у БД і адмінку; стабільні `id` у кожного елемента |
| D-022 | Контентна БД — PostgreSQL, як у crypto-bot | Замість SQLite v4: PostgreSQL 16 (`postgres:16-alpine`), SQLAlchemy 2 + psycopg 3 + Alembic. Правило D-005 не змінюється: лише підтверджені частини власних публікацій. JSON-поля — `JSONB`, час — `timestamptz`. `/state` і `/cache` лишаються файлами |
| D-023 | Production — окремий Docker-проєкт `news-digest` на тому ж VPS, що crypto-bot, з двома контейнерами: власний PostgreSQL (`db`) і бот (`app`) | Crypto-bot і його стек `postgres` не використовуються й не змінюються (вони лише для читання). Свої мережа, том, пароль, бекапи. Код — `/srv/news-digest`, `docker-compose.prod.yml`. Див. [deployment.md](deployment.md). Уточнено власником 2026-11-11: спершу планувалася спільна база в контейнері crypto-bot — відхилено |
| D-024 | Допис, опублікований у вікні, але відредагований після межі, береться в поточній версії | Замінює v4 §9 (`post_cutoff_edit` → виключення) і T20. Рішення власника 2026-11-11 після живого скану (3 з 89 дописів відкидались). `edit_date_utc` лишається в кеші; кількість таких дописів — окремий лічильник `edited_after_cutoff`. Час допису (для вікна, сортування, посилання) — час публікації, не редагування |
| D-025 | Стиль пункту: емодзі + жирний короткий заголовок, під ним суть у 1–2 реченнях, у кінці назва джерела-посилання | Власник затвердив макет 2026-11-11. Формат: `N. <емодзі> **Заголовок**` / `Суть. — Назва`. Заголовок випуску жирний; при N>1 — `· Частина i/N`. «Оновлення:» — на початку заголовка. Емодзі й заголовок пише модель |
| D-026 | Обмежень на токени/витрати OpenAI немає — ні зараз, ні найближчим часом | Рішення власника 2026-11-11. Бюджети v4 (per_digest/day, резервування, тарифна таблиця, блокування при перевищенні) не реалізуються. Поле `daily_budget_usd` у конфігу ігнорується. Токени кожного run лише записуються в `/state` для інформації. Не додавати лімітів без нової вказівки власника |
| D-027 | Пам'ять моделі про опубліковане — 24 години, а не 7 днів | Рішення власника 2026-11-11. Покриває «вчорашній вечірній випуск → ранкове вікно», менше токенів. Повтори поза 24 годинами модель не бачить. Відсіювання вже використаних дописів за ключем (ID каналу + номер повідомлення, D-012) працює незалежно й без обмеження в часі |

## Технічні defaults і деталізація

- Python 3.13, один worker, Telethon, PostgreSQL 16, JSON/JSONL, Docker Compose.
- Локальний PostgreSQL на хості — порт 5433 (5432 зайнятий crypto-bot). Підключення —
  змінні `POSTGRES_*`; у production пароль через `POSTGRES_PASSWORD_FILE`.
- Інструменти: uv/uv.lock, Typer, pytest/pytest-asyncio, Ruff, mypy;
  asyncio/zoneinfo scheduler, стандартний logging у JSON. Повна таблиця —
  [technology-stack.md](technology-stack.md). Це технічні defaults, не додаткові побажання власника.
- Ключі джерел усередині цільового каналу — `source_channels` і `source_sites`
  (вибір асистента 2026-11-11; власник може перейменувати).
- Промпт цільового каналу — файл `prompt_file` (рекомендовано) або коротке поле `prompt`.
- `filters.exclude_patterns` — прості підрядки без урахування регістру, не regex
  (вибір асистента 2026-11-11: без ризику повільних regex).
- Пакет `src/newsdigest`, збірка hatchling, CLI-коди виходу: 0 — OK, 2 — помилка
  конфігу, 3 — неправильні аргументи.
- Секрети (OpenAI key, Telegram `api_id`/`api_hash`, session) — не в JSON-конфігу, а в secret files.
- `Europe/Kyiv`, шаблон 08:00/21:00; розклади цільових каналів незалежні.
- Кеш: до завершення обробки, максимум 24 години від створення run; 512 MB;
  переживає restart, не входить у backup.
- Власні публікації: 365 днів; пам'ять повторів для моделі: 24 години (D-027); backup: 7 днів.
- `max_chars_per_message=3500`, 1–2 речення на подію, нумерація пунктів наскрізна.
- Частини готуються до першого send; кожна має власні `part_key` і `random_id`.
  За часткової доставки підтверджені частини залишаються опублікованими.
- Чистий `preview` одразу очищає кеш; окремий `prepare` зберігає готову серію
  до TTL для подальшого `publish --run-id`. Це усуває суперечність v4 §8/§22.
- Конфігурація schema 4 у JSON. Міграції з YAML schema 3 немає й не потрібно:
  legacy-конфігів не існує.
