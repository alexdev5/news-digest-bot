# NewsDigest: правила роботи в репозиторії

## Контекст і порядок читання

NewsDigest — Python-сервіс у Docker для тематичних дайджестів із Telegram-каналів
і сайтів. Документація українською зберігається в `docs/`. Цей файл описує роботу
асистентів із кодом, а не інструкції новинній моделі під час виконання.

**Спершу прочитай `docs/context.md`** — стислий контекст розмов із власником,
рішення й поточний стан. Після завершення своєї задачі онови його.

Перед змінами прочитай `docs/README.md`, `docs/specification.md` і потрібні
розділи `docs/architecture.md`. Для невирішених питань дивись `docs/decisions.md`
та `docs/review.md`; для перевірок — `docs/testing.md`.
Повний вибір технологій та інструментів — у `docs/technology-stack.md`.

Пріоритет: актуальні прямі вказівки власника → підтверджені рішення в
`docs/decisions.md` → поточний контракт `docs/specification.md` → початкове ТЗ
`docs/specs/newsdigest-v4.txt`. Технічні пропозиції не видавай за побажання власника.
Оригінал ТЗ залишай незмінним; уточнення внось у робочі документи з датою.

Стан на 2026-11-11: етап 1 і основна частина етапу 2 — JSON-конфіг, розклади й
ревізії, PostgreSQL (Alembic), `/state`, файловий кеш, сканер історії Telegram
(Telethon), worker `digest run` і команди login/dialogs/doctor/scan/status. Обробка
AI, рендер, публікація, сайти ще не реалізовані — не описуй їх як готові. Кореневий `main.py` — шаблон PyCharm,
не точка входу. Підтримуй цю примітку актуальною.

Команди проєкту — через обгортку в Docker, як у сусідньому проєкті crypto-bot:
`.\run.cmd <команда>` (Windows, делегує в `run.ps1`) або `./run.sh <команда>`
(Linux/macOS). Основні: `start`/`stop` (PostgreSQL), `migrate`, `psql`, `build`, `check`
(ruff + mypy + pytest), `test`, `lint`, `typecheck`, `validate`, `schedule`, `digest …`,
`shell`. Тести БД створюють і видаляють тимчасову базу; у Docker без БД вони падають. Нові операції додавай
одночасно в `run.ps1`, `run.cmd` (коментар) і `run.sh`. Без Docker — `uv run …`.

## Незмінні вимоги продукту

- Термін: **цільовий канал** — елемент `target_channels` JSON-конфігу (у ТЗ v4 —
  «профіль»): власний канал публікації зі своїми `source_channels`, `source_sites`,
  промптом, розкладом і `scan_start_at`.
- Один звичайний Telegram-акаунт читає джерела та публікує. Bot token не потрібний.
- Читати тільки явно налаштовані увімкнені джерела цільового каналу. Без auto-join,
  обходу всіх підписок, постійного ingestion і сканування при звичайному startup.
  Окремого реєстру прав немає: власник дозволив обробку публічних джерел (D-010).
- Сканувати (Telegram і сайти) на межі розкладу, під час дозволеного retry/catch-up
  або явного preview/prepare. Idle-перевірки та healthcheck не читають джерела.
- Вікна фіксовані, `[start,end)`, між сусідніми плановими межами; знизу обрізаються
  `scan_start_at`. Пропуск не розширює наступне вікно до часу останньої публікації.
- Сайти завантажуються лише з налаштованих доменів, із SSRF-захистом і лімітами.
- Включати **всі унікальні придатні новини**, а не тільки головні. Ліміти 8/6
  подій і відкидання за низькою важливістю з початкового ТЗ скасовані власником.
- Унікальність визначається за подією й фактами: різні формулювання однієї
  події змістово групує модель. Hash усуває тільки точні копії; текстова схожість
  не дозволяє втратити новий факт, інше місце/час, число або заперечення.
- Якщо випуск завеликий, публікувати послідовні частини `1/N`, `2/N`, … .
  Не обрізати набір подій, щоб умістити його в одне повідомлення.
- Один пункт: `короткий зміст — Назва джерела`; рівно назва є одним посиланням
  на конкретний допис/статтю. Посилання обирає код: **найраніший за часом
  публікації** придатний допис групи; рівний час → вище у списку джерел (D-015).
- Пункти в хронологічному порядку за найновішим дописом групи, найновіші внизу (D-016).
- Видимих технічних маркерів у пості немає; hash і ключі — у БД/`/state`.
  У БД частини є `source_message_ids` — ID використаних джерельних записів (D-014).
- Немає новин → нічого не публікувати. Допис, ID якого вже опубліковано в цьому
  цільовому каналі, не використовувати повторно (D-012). Неповний scan → публікувати
  прочитане без позначки (D-019). Допис, відредагований після межі, береться в
  поточній версії (D-024).
- Вхідні тексти, evidence, prompts, responses й чернетки — тільки в тимчасовому
  файловому кеші. У PostgreSQL — тільки підтверджені власні повідомлення та їхні
  metadata (D-022). Схема змінюється лише міграціями Alembic.
- Технічні файли `/state` не містять новинних текстів. Вони зберігають розклад,
  delivery guards, budgets і rate limits. Кеш не включається в backup.
- Пам'ять між випусками — тільки з уже опублікованих власних пунктів.
- AI: OpenAI Responses API, `gpt-5.6-sol`, `reasoning.effort=medium`; цільовий канал
  може явно перевизначити модель. Не підміняй модель або провайдера мовчки.
  Rule-based заміни AI в MVP немає: AI-збій → випуск не виходить, alert (D-011).
- Промпт цільового каналу доповнює системні інструкції, не скасовує structured
  output, обов'язкові refs і захист від prompt injection.
- Модель не отримує tools, секрети, Telegram-сесію, shell або право самостійно
  надсилати повідомлення. `store=false` не є обіцянкою ZDR.

## Межі модулів і доставки

Стек: Python 3.13, asyncio, Telethon, Pydantic, JSON-конфіг (schema 4,
`target_channels`), офіційний async OpenAI SDK, PostgreSQL 16 (SQLAlchemy 2, psycopg 3,
Alembic — як у crypto-bot), JSON/JSONL, Docker Compose;
для сайтів — кандидати httpx, feedparser, selectolax, trafilatura. Версії фіксуй після
перевірки сумісності. Не додавай Redis, Celery, вебпанель або інший стек без потреби
задачі. Конфіг проєктуй так, щоб його модель можна було згодом читати з БД (адмінка).
Інструментальні defaults: uv/uv.lock, Typer, pytest/pytest-asyncio, Ruff, mypy;
планувальник на asyncio/zoneinfo, логи через стандартний logging у JSON.

Scheduler визначає вікна; scanner читає історію; pipeline обробляє кеш;
attribution обирає джерело; renderer формує текст/entities і частини;
publisher надсилає; repository приймає лише підтверджену публікацію.
Детальний контракт серій — у `docs/architecture.md`.

- Розрізняй випуск (`digest_key`) і Telegram-повідомлення (`part_key`).
- Перед першим send зафіксуй увесь план частин, payload, hashes і random IDs.
- Кожна частина має власний guard, random ID, receipt і рядок у БД після ack.
- Після `sending/uncertain` спочатку reconciliation. Не генеруй інший payload
  і не повторюй підтверджені частини. DB commit failure не дозволяє новий send.
- Не обіцяй атомарної доставки всієї серії або exactly-once за будь-якого збою.
- Кеш успішної серії очищай після підтвердження й запису всіх частин; невдалий
  кеш має обмежений TTL. Unresolved guards переживають TTL без контенту.
- Atomic state writes, process lock і per-profile ordering — обов'язкові.

## Робочий процес і перевірки

1. Знайди релевантні вимоги й тести; не перебудовуй непов'язані частини проєкту.
2. Змінюй контракт, приклади, схеми та перевірки разом. Нові рішення записуй у
   `docs/decisions.md`; результати реалізації — у `docs/implementation-plan.md`;
   короткий підсумок розмови/етапу — у `docs/context.md`.
3. Для коду використовуй type hints і явні моделі стану; відділяй чисту логіку
   вікон/форматування від зовнішнього I/O. Не блокуй asyncio синхронним I/O.
4. Перевіряй поведінку зі збоями, межі часу, Unicode, повноту й відсутність raw
   у постійних даних. Для документації достатньо перевірити посилання й узгодженість.
5. Запускай лише наявні команди проєкту. Не вигадуй успішні тести й не заявляй
   готовність частин сервісу, яких ще немає.
6. Звичайні тести — офлайн із синтетичними даними. Реальні платні probes та
   публікації виконуються лише в межах явно поставленої задачі й налаштованого бюджету.
7. Не логуй/не коміть секрети, session, тексти джерел або робочий кеш. Не видаляй
   дані власника й не виконуй реальні міграції лише через наявність опису в ТЗ.

## Git

- Ніколи не комітити без прямої команди власника.
- Push робить тільки власник. Асистенти не виконують `git push` у жодному вигляді.
- Повідомлення коміту — максимально коротке, як від розробника-людини. Без згадок
  AI, ботів, агентів, асистентів, без `Co-Authored-By` та інших attribution-рядків.

Проєкт `C:\OSPanel\domains\crypto-bot` і його стеки на сервері — **тільки для читання**
(вказівка власника 2026-11-11): звідти можна брати приклади, але нічого не змінювати.

Production: той самий VPS, що crypto-bot, але окремий Docker-проєкт `news-digest`
із двома контейнерами — власний PostgreSQL (`db`) і бот (`app`), D-023. Спільних
мереж, баз чи томів із crypto-bot немає. Порядок — `docs/deployment.md`.

Основна документація — тільки в `docs/`; кореневий `README.md` залишається
короткою точкою входу. Оновлюй документацію разом із поведінкою, яку змінюєш.
