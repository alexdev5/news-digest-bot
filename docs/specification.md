# Поточний контракт NewsDigest

Дата: 2026-11-11. База — [ТЗ v4](specs/newsdigest-v4.txt) із рішеннями власника
[D-001–D-021](decisions.md). Цей документ змінює відповідні місця оригіналу;
незмінені деталі v4 (DST, reload, TTL, backup, recovery) залишаються чинними.
Терміни: **цільовий канал** = елемент `target_channels` (у v4 — «профіль»);
**джерело** = Telegram-канал із `source_channels` або сайт із `source_sites`.

## Призначення

Один звичайний Telegram-акаунт за розкладом читає налаштовані Telegram-канали,
сервіс завантажує налаштовані сайти, модель `gpt-6.1-terra` групує й стисло
переказує всі унікальні новини, а сервіс публікує результат у цільовий канал.
Кожен цільовий канал має свої джерела, промпт, розклад і правила. Новий канал
додається новим елементом JSON-конфігу без правок коду.

У MVP немає bot token, вебпанелі, auto-join, архіву джерел, постійного collection,
OCR, транскрипції, статусних постів «новин немає» або позапланових breaking-news.

## Права на джерела (D-010)

Публічні канали, на які підписаний акаунт, і налаштовані сайти власник дозволив
читати, обробляти AI й стисло публікувати у власний канал. Окремий реєстр прав
v4 не реалізується; джерело вмикається/вимикається полем `enabled`. Вимкнене
джерело не читається й не передається моделі. Захисні обмеження Telegram
(protected content) не обходяться.

## Що означає «всі унікальні новини»

У випуск входять усі події, які:

1. Отримані з увімкнених джерел цільового каналу у його вікні.
2. Мають придатний текст, відповідають темі та не є рекламою або service message.
3. Не є повтором іншої події цього випуску або вже опублікованого факту без розвитку.
4. Мають перевірені references та достатню опору для коректного короткого викладу.

Десять копій однієї події дають один пункт; суттєвий розвиток попередньої
події — пункт «Оновлення». Важливість не впливає ні на відбір, ні на порядок.

Різні тексти можуть описувати ту саму подію. Змістове групування й короткий
огляд робить модель (D-009). «У місті відновили електропостачання» й «Світло
повернули мешканцям міста» утворюють один пункт, якщо час/місце/подія збігаються.
Додатковий факт із другого допису враховується; інша подія, нове число,
спростування або розвиток не губляться через схожі слова.

Робочий потік: усі придатні тексти за вікно → модель → структуровані події
та короткий виклад → перевірка references/фактів → attribution → форматування/поділ
→ відправка. Модель готує зміст; Telegram-виклик робить сервіс після перевірок.
Якщо обсяг не вміщується в один запит, використовуються пачки з фінальним
змістовим узгодженням без втрати відмінних новин.

Локально можна об'єднати точні текстові копії, зберігши всі refs. Текстова
схожість — лише підказка, не підстава видалити відмінний зміст до AI.
`selection_mode=important`, ліміти 8/6 і `low_priority` як причина вилучення не діють.

**Повтори за ID (D-012).** Джерельний допис або стаття, ID якого вже є в
`source_message_ids` опублікованих частин цього цільового каналу, повторно не
використовується. Для Telegram ID — `(peer_id, message_id)`, для сайту —
канонічний URL статті.

## Розклади та історія

- Підтримуються незалежні `daily_slots` і `fixed_interval`, як у v4 §7.
- Вікно — `[попередня планова межа, поточна планова межа)`; час у стані — UTC.
- **D-029:** якщо частину цього інтервалу вже покрив ручний прогін (або інше
  опубліковане/зібране вікно), початок зсувається на кінець покритого:
  `[max(попередня межа, покрите), межа)`. Невдалі runs покритими не вважаються.
- **Ручний прогін `run-now` (D-029):** вікно `[max(найближча минула межа, покрите,
  scan_start_at), зараз)` — сканування, AI, публікація. Наприклад, межі 08/15/21,
  публікацій ще не було, зараз 17:10 → 15:00–17:10; опубліковано о 08:00, зараз 12:00 →
  08:00–12:00, а межа 15:00 потім бере 12:00–15:00.
- **`scan_start_at` (D-013):** раніше цього моменту нічого не читається. Вікно
  обрізається знизу: `[max(попередня межа, scan_start_at), межа)`. Межі до
  `scan_start_at` не створюють випусків.
- Перший startup реєструє наступну межу; історію до її настання не читає.
- На cutoff починається paginated scan до початку вікна, а не лише останніх 100 постів.
- Retry/catch-up зберігає початкові межі. Default grace — 3 години; старіші
  misfires пропускаються з технічним записом, без розширення наступного вікна.
- Перевизначення розкладу завершує старе відкрите вікно, потім створює перехідне `[C,N)`.
- Спільне джерело кількох цільових каналів читається один раз для одночасно належних runs.
- Між запусками немає source-history polling, RSS-опитування чи накопичення updates.

Приклад 08:00/21:00 за Києвом: ранковий випуск охоплює вчора 21:00–сьогодні
08:00, вечірній — 08:00–21:00. Пост рівно о 08:00 належить вечірньому вікну.

**Редагування (D-024).** Належність до вікна визначає час публікації. Допис із
вікна, відредагований уже після межі, не відкидається: береться його поточна версія
(старіша недоступна). У кеші зберігається `edit_date_utc`, у підсумку скану —
лічильник `edited_after_cutoff`. Редагування старого допису не переносить його в нове вікно.

## Сайти як джерела (D-020)

- Для кожного сайту: `rss` (RSS/Atom), якщо є; інакше `url` сторінки-списку і
  `selectors` для посилань, заголовка, дати й тексту статті.
- На межі вікна сервіс читає RSS або сторінку-список, відбирає статті з датою
  публікації в `[start,end)`, завантажує їх, очищає HTML до тексту.
- Стаття без надійної дати публікації не включається (технічна причина `no_date`).
- Завантажуються лише URL налаштованих доменів; redirect на інший домен,
  localhost, приватні IP, `file://` та нестандартні схеми блокуються (v4 §20).
  Обмеження розміру відповіді й таймаути обов'язкові.
- Тексти статей — тільки в тимчасовому кеші, як і Telegram-дописи.

## Формат і поділ

Один логічний випуск складається з однієї або кількох текстових частин.
Для N>1 кожна містить заголовок, назву цільового каналу, період і `Частина i/N`.
Для N=1 позначка частини не виводиться. Пункти нумеруються наскрізно.
Видимих технічних маркерів/хештегів немає (D-014).

Формат пункту (D-025):

> 1. ⚡ **Короткий заголовок**
> Суть новини в 1–2 реченнях. — Назва джерела

Заголовок — жирний (bold entity), до ~80 символів, без крапки; емодзі — один,
доречний. Рівно назва джерела є одним прихованим посиланням (text URL entity) на
конкретний допис або статтю. Для розвитку вже опублікованої події заголовок
починається з «Оновлення:». Заголовок випуску теж жирний. Пункти розділені
порожнім рядком.

**Вибір посилання (D-015).** Серед придатних учасників події обирається допис
із найменшим часом публікації; посилання веде на нього. За рівного часу —
джерело вище в списку (`source_channels` у їх порядку, потім `source_sites`).
Назва — `name` із конфігу, інакше title каналу з Telegram або назва сайту.
Вибір робить код, не модель. Факти, відомі тільки з іншого джерела,
атрибутуються в реченні («за повідомленням …») або не додаються.

**Порядок пунктів (D-016).** За зростанням часу найновішого допису групи:
найновіші новини внизу, як у стрічці Telegram. Рівний час — стабільний
tie-break за ID події.

Поділ виконується **між цілими пунктами**, після рендерингу тексту й entities.
Бюджет частини враховує заголовок, `i/N`, назви джерел і пропуски.
Після визначення N повторити packing, доки всі частини вкладаються з кінцевими
заголовками.

Ліміт `max_chars_per_message=3500` застосовується до кожної частини, додатково
перевіряється runtime-ліміт Telegram. Entities рахуються в UTF-16. Окремий
завеликий пункт скорочується без втрати змісту й атрибуції; якщо неможливо —
явна помилка, не мовчазне відкидання новини. Прихованого `max_parts` немає.
Link preview вимкнено.

Перед першим send у кеші вже є весь незмінний план серії. Частини надсилаються
послідовно під lock цільового каналу; інші цільові канали незалежні.

## Порожній і неповний результат (D-012, D-019)

- Немає придатних новин за вікно → **нічого не публікується**, у `/state`
  фіксується результат `empty`.
- Частину джерел не вдалося прочитати → публікується те, що прочитано, без
  позначки в пості. Неповнота (`partial`) пишеться тільки в технічний журнал/`/state`.
- AI недоступний або повернув невалідний результат (D-011) → bounded retry у
  межах вікна/grace; далі випуск не публікується, технічне сповіщення власнику.
  Rule-based заміни AI в MVP немає.

## Дані й підтвердження

| Де | Що | Життєвий цикл |
| --- | --- | --- |
| `/cache` | Вхідні дописи й статті, candidates, evidence, AI-дані, готові частини | До завершення серії; за збоїв до TTL, default 24 години |
| PostgreSQL, таблиця `published_messages` | Власні підтверджені Telegram-повідомлення, їхні пункти й `source_message_ids` | Default 365 днів |
| `/state` | Розклади, pinned peers, guards частин, counters/reservations, rate limits | Між запусками; unresolved guards не видаляються за TTL кешу |
| `/session` | Авторизаційна сесія Telegram-клієнта | Постійно; окремий режим захисту й backup |

У контентній БД — один рядок на **підтверджену частину**. `digest_key` визначає
цільовий канал/вікно; `part_key` — конкретну частину. Payload hash зберігається
в БД, не в тексті поста. Поле `source_message_ids` — масив ID усіх джерельних
дописів/статей, використаних у пунктах цієї частини (D-014).
Правила ідемпотентності, індекси та recovery — в [архітектурі](architecture.md).
Не створювати таблиці pending/failed runs або raw outbox у БД. Контентна БД —
PostgreSQL (D-022); схема змінюється тільки міграціями Alembic.

Пам'ять між випусками — тільки з пунктів підтверджених частин. Підтверджені
повідомлення не видаляються автоматично для імітації атомарної операції.

**Звірка (D-017).** Після таймауту надсилання в цільовому каналі шукається власний
пост акаунта в очікуваному часовому інтервалі після переходу в `sending`.
Текст не порівнюється. Рівно один кандидат → confirmed (`reconciled`); нуль або
більше одного → `uncertain`, наступні частини й новіший випуск цього цільового
каналу не надсилаються до ручного рішення. Після DB commit failure відновлюється
запис уже доставленого, а не повторюється send.

Кеш очищається після commit усіх частин і звільнення shared references.
На TTL незавершеної серії зупинити обробку, видалити контент, зберегти
безконтентні guards; за вже розпочатого send автоматичної регенерації немає.

## AI

OpenAI Responses API, за замовчуванням `model=gpt-6.1-terra`,
`reasoning.effort=medium`; цільовий канал може явно перевизначити модель/effort.
Промпт цільового каналу (`prompt_file`/`prompt`) доповнює, а не замінює системні
інструкції сервісу: формат structured output, обов'язкові refs, заборону вигадувати
факти й захист від prompt injection. Strict schema кожної стадії; `store=false`,
`stream=false`, tools відсутні. Фактичний model ID і numeric usage записуються
в metadata. Ключ і бюджет потрібні для реальних викликів, а не для написання коду.

Обробка пачками з міжпачковою дедуплікацією. Модель не має права залишити лише
«найважливіші». Облік придатних, відхилених (з причиною), включених і
необроблених подій зберігається до очищення кешу.

## Preview і підготовка до надсилання

- `preview`: явне читання/обробка, показ результату, без send, guards і DB insert;
  після успіху кеш очищається.
- `prepare`: та сама підготовка зі збереженням кешу до TTL; повертає run ID.
- `publish --run-id ... --confirm`: перевіряє TTL, цільовий канал, вікно,
  попередні публікації/guards і надсилає збережений payload.
- Production за розкладом проходить prepare→send без ручного preview.

## Конфігурація: JSON schema 4 (D-021)

Файл `config/config.json`. Невідомі поля й дублікати ключів — помилка валідації.
Значення з `defaults` успадковуються цільовим каналом, якщо він їх не перевизначив;
списки (`times`, `source_channels`, `source_sites`) замінюються цілком.

```json
{
  "schema_version": 4,
  "defaults": {
    "timezone": "Europe/Kyiv",
    "ai": { "model": "gpt-6.1-terra", "reasoning_effort": "medium", "max_output_tokens": 8192 },
    "publication": { "max_chars_per_message": 3500, "link_preview": false }
  },
  "target_channels": [
    {
      "id": "dnipro_news",
      "enabled": true,
      "name": "Новини Дніпра",
      "description": "Події Дніпра та області",
      "telegram": "@my_dnipro_digest",
      "schedule": { "times": ["08:00", "21:00"], "timezone": "Europe/Kyiv" },
      "scan_start_at": "2026-11-12T00:00:00+02:00",
      "source_channels": [
        { "id": "hdnipro", "enabled": true, "ref": "@hdnipro", "name": "ХДніпро" }
      ],
      "source_sites": [
        { "id": "example_ua", "enabled": true, "name": "Example.ua",
          "url": "https://example.ua/news", "rss": null, "selectors": null }
      ],
      "ai": { "prompt_file": "prompts/news-ua.md" },
      "filters": { "exclude_patterns": ["реклама", "розіграш"] },
      "format": { "header": "{name} · {date} {time}" },
      "daily_budget_usd": 1.0
    }
  ]
}
```

Це **приклад контракту** з демонстраційними значеннями, не робоча конфігурація.
Повний робочий приклад — `config/config.example.json`; власний конфіг
`config/config.json` не комітиться. Правила:

- `id` — стабільний ключ (латиниця, цифри, `_`), унікальний у своєму списку;
  не змінюється при перейменуванні. Потрібний для майбутнього переносу в БД/адмінку.
- `telegram` і `ref` — `@username`, `https://t.me/<username>` або marked ID
  `-100…`; після першого підтвердження peer закріплюється (v4 §6).
- `schedule`: або `times` (+`timezone`), або `every_seconds` + `anchor_at`
  з явним UTC offset; змішувати не можна.
- `scan_start_at` — ISO 8601 з явним UTC offset.
- `misfire_grace_seconds` — у `defaults` (default 10800) або в `schedule` каналу.
- Сайт потребує `rss` або `selectors` (`item` — обов'язковий CSS-селектор посилань
  на статті; `title`, `date`, `content` — необов'язкові).
- `filters.exclude_patterns` — підрядки без урахування регістру, не regex.
- `format.header` дозволяє лише поля `{name}`, `{date}`, `{time}`, `{period}`.
- `prompt_file` — шлях відносно теки конфігу й лише всередині неї.
- Цільовий канал не може бути джерелом жодного цільового каналу; цільові канали різні.
- Секрети в конфігу заборонені; шляхи до secret files задаються окремо в
  налаштуваннях застосунку.
