# NewsDigest: правила роботи в репозиторії

## Контекст і порядок читання

NewsDigest — Python-сервіс у Docker для тематичних дайджестів із Telegram.
Документація українською зберігається в `docs/`. Цей файл описує роботу
асистентів із кодом, а не інструкції новинній моделі під час виконання.

Перед змінами прочитай `docs/README.md`, `docs/specification.md` і потрібні
розділи `docs/architecture.md`. Для невирішених питань дивись `docs/decisions.md`
та `docs/review.md`; для перевірок — `docs/testing.md`.
Повний вибір технологій та інструментів — у `docs/technology-stack.md`.

Пріоритет: актуальні прямі вказівки власника → підтверджені рішення в
`docs/decisions.md` → поточний контракт `docs/specification.md` → початкове ТЗ
`docs/specs/newsdigest-v4.txt`. Технічні пропозиції не видавай за побажання власника.
Оригінал ТЗ залишай незмінним; уточнення внось у робочі документи з датою.

На дату 2026-11-11 реалізації NewsDigest ще немає: кореневий `main.py` — шаблон
PyCharm. Не описуй заплановані CLI, Dockerfile, тести чи API-інтеграції як готові.
Підтримуй цю примітку актуальною після появи реалізації.

## Незмінні вимоги продукту

- Один звичайний Telegram-акаунт читає джерела та публікує. Bot token не потрібний.
- Читати тільки явно налаштовані джерела активного профілю. Без auto-join,
  обходу всіх підписок, постійного ingestion і сканування при звичайному startup.
- Сканувати на межі розкладу, під час дозволеного retry/catch-up або явного
  preview/prepare. Idle-перевірки та healthcheck не читають історію джерел.
- Вікна фіксовані, `[start,end)`, між сусідніми плановими межами профілю.
  Пропуск не розширює наступне вікно до часу останньої успішної публікації.
- Включати **всі унікальні придатні новини**, а не тільки головні. Ліміти 8/6
  подій і відкидання за низькою важливістю з початкового ТЗ скасовані власником.
- Унікальність визначається за подією й фактами: різні формулювання однієї
  події змістово групує модель. Hash усуває тільки точні копії; текстова схожість
  не дозволяє втратити новий факт, інше місце/час, число або заперечення.
- Якщо випуск завеликий, публікувати послідовні частини `1/N`, `2/N`, … .
  Не обрізати набір подій, щоб умістити його в одне повідомлення.
- Один пункт: `короткий зміст — Назва каналу`; рівно назва є одним посиланням
  на конкретний допис. Видиме джерело обирає код за порядком `source_ids`
  серед реальних придатних учасників події, а не LLM або `priority`.
- Вхідні тексти, evidence, prompts, responses й чернетки — тільки в тимчасовому
  файловому кеші. У SQLite — тільки підтверджені власні повідомлення та їхні metadata.
- Технічні файли `/state` не містять новинних текстів. Вони зберігають розклад,
  delivery guards, budgets і rate limits. Кеш не включається в backup.
- Пам'ять між випусками — тільки з уже опублікованих власних пунктів.
- Основний AI: OpenAI Responses API, `gpt-5.6-sol`, `reasoning.effort=medium`.
  Збережи точний model ID; не підміняй модель або провайдера мовчки.
- Модель отримує лише дозволені дані, не отримує tools, секрети, Telegram-сесію,
  shell або право самостійно надсилати повідомлення. `store=false` не є обіцянкою ZDR.
- Права джерел перевіряються також для rule-based режиму; fallback не обходить їх.

## Межі модулів і доставки

Стек: Python 3.13, asyncio, Telethon, Pydantic, безпечний YAML, офіційний
async OpenAI SDK, SQLite, JSON/JSONL, Docker Compose. Версії фіксуй після перевірки
сумісності. Не додавай Redis, Celery, вебпанель або інший стек без потреби задачі.
Інструментальні defaults: uv/uv.lock, Typer, pytest/pytest-asyncio, Ruff, mypy;
планувальник на asyncio/zoneinfo, логи через стандартний logging у JSON.

Scheduler визначає вікна; scanner читає історію; pipeline обробляє кеш;
attribution обирає джерело; renderer формує текст/entities і частини;
publisher надсилає; repository приймає лише підтверджену публікацію.
Детальний контракт серій — у `docs/architecture.md`.

- Розрізняй випуск (`digest_key`) і Telegram-повідомлення (`part_key`).
- Перед першим send зафіксуй увесь план частин, payload, hashes і random IDs.
- Кожна частина має власний guard, random ID, receipt і рядок у БД після ack.
- Після `sending/uncertain` спочатку reconciliation. Не генеруй інший payload
  і не повторюй підтверджені частини. DB commit failure не дозволяє новий send.
- Не обіцяй атомарної доставки всієї серії або exactly-once за будь-якого збою.
- Кеш успішної серії очищай після підтвердження й запису всіх частин; невдалий
  кеш має обмежений TTL. Unresolved guards переживають TTL без контенту.
- Atomic state writes, process lock і per-profile ordering — обов'язкові.

## Робочий процес і перевірки

1. Знайди релевантні вимоги й тести; не перебудовуй непов'язані частини проєкту.
2. Змінюй контракт, приклади, схеми та перевірки разом. Нові рішення записуй у
   `docs/decisions.md`; результати реалізації — у `docs/implementation-plan.md`.
3. Для коду використовуй type hints і явні моделі стану; відділяй чисту логіку
   вікон/форматування від зовнішнього I/O. Не блокуй asyncio синхронним I/O.
4. Перевіряй поведінку зі збоями, межі часу, Unicode, повноту й відсутність raw
   у постійних даних. Для документації достатньо перевірити посилання й узгодженість.
5. Запускай лише наявні команди проєкту. Не вигадуй успішні тести; поки немає
   `pyproject.toml`/test suite, не заявляй про запуск `pytest` чи готовність сервісу.
6. Звичайні тести — офлайн із синтетичними даними. Реальні платні probes та
   публікації виконуються лише в межах явно поставленої задачі й налаштованого бюджету.
7. Не логуй/не коміть секрети, session, тексти джерел або робочий кеш. Не видаляй
   дані власника й не виконуй реальні міграції лише через наявність опису в ТЗ.

Основна документація — тільки в `docs/`; кореневий `README.md` залишається
короткою точкою входу. Оновлюй документацію разом із поведінкою, яку змінюєш.
