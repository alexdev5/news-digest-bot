01. МЕТА ПРОЄКТУ ТА ОЧІКУВАНИЙ РЕЗУЛЬТАТ
==============================================================================

Розробити Docker-застосунок NewsDigest для тематичних зведень із Telegram.
Один окремий ЗВИЧАЙНИЙ Telegram-акаунт читає явно налаштовані джерела і публікує
результат у каналах власника. BotFather і bot token не потрібні.

Приклади незалежних профілів:
  «Україна» → свій упорядкований список джерел → свій канал зведень;
  «Криптовалюти» → інший список → інший канал;
  наступна тема → новий профіль у YAML без правок коду.

Кожен профіль має власний розклад. Початковий шаблон — 08:00 і 21:00,
Europe/Kyiv: ранкове вікно [вчора 21:00, сьогодні 08:00), вечірнє —
[сьогодні 08:00, сьогодні 21:00). Можливі інші години, кількість слотів,
часові зони або інтервал «кожні N секунд» від заданої точки відліку.

НОВА БАЗОВА СХЕМА:
  планова межа профілю → сканування його часового вікна → тимчасовий кеш
  → фільтри й об'єднання → OpenAI API / GPT-5.6 Sol → перевірка й оформлення
  → публікація у Telegram → підтвердження доставки → запис опублікованого
  повідомлення в БД → очищення більше не потрібного кешу.

Постійного читання чужих каналів немає. Джерела не скануються кожні 5 хвилин
і не записуються через фоновий NewMessage-listener. Процес може працювати
постійно як планувальник, але читати новини він починає тільки для належного
випуску, його обмеженого retry/catch-up або явного ручного preview.

База застосунку містить ТІЛЬКИ підтверджені власні публікації та їхні metadata.
Оригінали зчитаних постів, чернетки, відхилені кандидати, результати проміжної
AI-обробки й незавершені запуски у цю БД не потрапляють.

Один випуск — одне текстове повідомлення з кількома короткими пунктами.
Кожен пункт: «Короткий зміст новини — Назва каналу». Назва є прихованим
гіперпосиланням на КОНКРЕТНИЙ допис, не просто на сторінку каналу.
Кілька дописів про ту саму подію → один пункт і одне видиме посилання.
Для нього вибирається перший канал у profiles.<id>.source_ids серед каналів,
дописи яких реально використані для цієї події. Порядок списку має значення.

Терміни:
  source — канал-джерело; destination — власний канал публікації;
  profile — тема, упорядковані джерела, розклад, правила й destination;
  window — точний інтервал [start,end); run — один запуск обробки цього вікна;
  event — одна подія, можливо з кількох постів; digest — весь готовий випуск;
  published message — підтверджений вихідний Telegram-пост застосунку;
  temporary cache — тимчасові файли активної обробки, не архів новин;
  service state — мінімальний технічний стан без текстів вхідних новин.

Тлумачення «кожного поста» до уточнення: коротко переказується кожна відібрана
унікальна новина всередині зведення, а не створюється окремий вихідний пост
на кожен вхідний. Попередній відбір головного та ліміти 8/6 подій збережені
як робочий default, НЕ як уже підтверджена відповідь на питання «усі чи головні».
Див. розділи 13 і 28.

Це ТЗ, не готовий застосунок. CLI, поля конфігурації, схеми та числові пороги
нижче — контракт/проєктні параметри, а не заявлені квоти зовнішніх сервісів.

02. ЗАФІКСОВАНІ ВИМОГИ ТА ПРОЄКТНІ РІШЕННЯ
==============================================================================

FR-01. Один окремий звичайний Telegram-акаунт; читання й публікація через нього.
FR-02. Власник вступає до джерел вручну. Автоматичного join немає.
FR-03. Джерела — @username, URL каналу або marked ID у YAML; усі підписки
автоматично не скануються. Збір обмежений джерелами активного профілю.
FR-04. Кожен профіль має свій destination та впорядкований source_ids.
Один peer може належати кільком профілям, але не створює дубль вихідної новини.
FR-05. Акаунт має право публікувати у destinations. Власник/адміністратор із
post_messages може надсилати повідомлення в канал через API. [Д4, Д5]
FR-06. Незалежні daily_slots/fixed_interval, timezone і допуски кожного профілю
працюють уже в MVP. 08:00/21:00 — default, не глобальне обмеження.
FR-07. Сканування починається на плановій межі, за незмінним [start,end).
Немає фонового collection/update ingestion і періодичного опитування джерел.
FR-08. Зчитані пости та похідні неопубліковані дані — лише тимчасовий кеш.
FR-09. У БД — лише підтверджені власні публікації й metadata саме цих публікацій.
Невдала спроба, preview або чернетка не створює рядок у БД.
FR-10. Один випуск — один вихідний пост. Restart/retry не повинен давати дубль.
FR-11. Формат пункту: короткий зміст, пробіл, тире «—», пробіл, назва каналу.
Рівно назва каналу є гіперпосиланням на використаний Telegram-допис.
FR-12. Для об'єднаної події видимий канал обирається за порядком source_ids
цього профілю, а не за часом публікації, priority, популярністю або вибором LLM.
FR-13. Український редакторський текст, один-два короткі речення на подію;
дублікати зливаються, розвиток уже опублікованої події включається як оновлення.
FR-14. Основний AI-режим — OpenAI Responses API / GPT-5.6 Sol,
model=gpt-5.6-sol. Модель конфігурована, прихована підміна заборонена. [Д20]
FR-15. rule_based — явно позначений резервний режим; права перевіряються
незалежно від режиму. Секрети не зберігаються в YAML/репозиторії.
FR-16. Preview не надсилає пост і не поповнює БД. Він може витрачати AI-бюджет
і користується тим самим тимчасовим кешем із TTL.
FR-17. Пам'ять між випусками формується з уже опублікованих пунктів у БД,
а не з постійного архіву зчитаних джерел.
FR-18. Розклади, мінімальні delivery guards і лічильники бюджету зберігаються
окремими службовими файлами без новинних текстів; див. розділи 14 і 18.
FR-19. Кеш очищається після завершення й звільнення всіх поточних споживачів;
для незавершеного/невдалого run діє обмежений TTL. У backup кеш не включається.
FR-20. Зміна розкладу або порядку джерел не переписує snapshot відкритого вікна.
Статуси неповноти, відсутності новин і технічної помилки не підміняють один одного.

Контрольний масштаб першої версії: один сервер, один worker, один акаунт,
до 50 унікальних джерел і 5 профілів. Це сценарій тестування, не межа продукту.

03. УМОВИ ВИКОРИСТАННЯ КОНТЕНТУ ТА ОБМЕЖЕННЯ
==============================================================================

Важливе уточнення до початкової ідеї: технічний доступ до каналу не означає
автоматичного дозволу використовувати його контент у ШІ або перевидавати його.

Telegram API Terms поширюють на API умови Content Licensing and AI Scraping.
Умови містять широку заборону використання отриманих із Telegram даних для
розроблення, вдосконалення та deployment AI/ML. Окремо описано можливість винятків
за явною, поінформованою, чинною згодою всіх відповідних користувачів у конкретному
контексті. Вимоги правовласників також підлягають дотриманню. [Д1, Д2]

Проєкт не повинен трактувати «це лише inference», «модель локальна», «канал
публічний» або «я підписаний» як готовий дозвіл. Це обережний проєктний висновок
із формулювань правил, а не висновок про законність конкретного джерела. [Д1, Д2]

Реалізувати окремий реєстр прав і обмежень для кожного джерела:
  • підстава доступу й читання;
  • статус дозволу на повторне оприлюднення;
  • статус дозволу на AI-обробку;
  • посилання на підтвердження, дата перевірки та строк дії, якщо він є;
  • дозволені провайдери обробки, якщо дозвіл має таке обмеження.

За замовчуванням AI-обробка заборонена. Значення approved у конфігурації — запис
результату перевірки, а не спосіб створити дозвіл одним перемикачем.

Не передавати неузгоджений текст у LLM, embeddings, ML-класифікатор або локальну
нейромережу. Для такого тексту передбачено лише дозволену обробку правилами.
Вона також не є автоматичним дозволом на збір або публічне копіювання матеріалів.

Для приватних джерел та джерел із захистом контенту встановити блокування
експорту за замовчуванням. Не обходити технічні обмеження. Дозвіл адмініструвати
канал призначення не надає прав на матеріали каналів-джерел.

Якщо для бажаних Telegram-джерел немає підстав для AI-обробки, повноцінне
ШІ-зведення можна будувати з окремо дозволених RSS/API/матеріалів видавців.
Це інший адаптер джерел, а не спосіб «відмити» походження Telegram-тексту.

04. АРХІТЕКТУРА ТА ТЕХНОЛОГІЧНИЙ СТЕК
==============================================================================

Стек:
  Python 3.13; Telethon сумісної стабільної версії; asyncio;
  SQLite тільки для published_messages; файловий кеш JSON/JSONL;
  YAML safe loader + Pydantic; офіційний Python SDK openai;
  Docker Compose; структуровані логи й локальний CLI. [Д18, Д19, Д22]
Залежності й образ зафіксувати, не використовувати latest.

Модулі:
  scheduler — чекає меж профілів, не читає новини;
  history_scanner — у межах належного run читає історію за потрібним періодом;
  cache — тимчасові джерела, cursor, snapshot, кандидати, AI-результат, чернетка;
  pipeline — очищення, дедуплікація, ранжування, AI, перевірка фактів;
  attribution — детермінований вибір одного видимого джерела за source_ids;
  renderer — текст і Telegram entities;
  publisher — відправка й reconciliation;
  published_repository — запис лише ПІСЛЯ підтвердження публікації;
  service_state — технічні розклади, блокування повторів і бюджети без контенту.

Розмежування зберігання:
  /data/published.sqlite3 — підтверджені вихідні пости;
  /cache/runs/ та /cache/shared/ — тимчасові дані поточних запусків;
  /state/ — мінімальні JSON-файли технічного стану, без вхідних текстів;
  /session/ — авторизаційна сесія Telethon; це не контентна БД застосунку;
  /config/ — YAML, версії конфігурації й перевірені тарифи, без API-ключів.

Планувальник може прокидатися кожні 5 секунд для порівняння часу з розкладом.
Це НЕ опитування Telegram-каналів. Між випусками немає getHistory-запитів до
джерел, NewMessage/MessageEdited-listeners для збирання новин чи фонової звірки.
Протокольна робота Telegram-клієнта не повинна перетворюватися на ingestion.
Очищення TTL, heartbeat, резервне копіювання й облік бюджету можуть працювати
між випусками: вони не зчитують джерельні пости. Reconciliation власного
destination після невизначеного send — також окрема технічна операція.
За замовчуванням від'єднувати клієнт, коли немає активних Telegram-операцій.

Єдиний worker володіє Telegram-сесією і service-state writer lock.
Синхронні важкі дії не блокують планувальник. Спільна обмежена черга API-запитів
обслуговує профілі справедливо; конкретний run завжди ізольований за snapshot.

Для одночасно належних профілів можна звести читання спільного джерела до
одного сканування об'єднаного діапазону. Кожен run фільтрує свої [start,end).
Це оптимізація ОДНОГО активного scan batch, не привід зберігати історію між
випусками. Різні години публікації можуть потребувати повторного читання джерела.

Не потрібні Redis, Celery, Kubernetes, векторна БД або вебпанель.
Інтерфейси модулів мають дозволяти заміну сховища власних публікацій без зміни
редакторських правил, але не створювати прихований постійний архів новин.

==============================================================================
05. АКАУНТ, АВТОРИЗАЦІЯ ТА ПРАВА
==============================================================================

Початкова підготовка власником:
  1. Залишити окремий акаунт під власним контролем і ввімкнути 2FA.
  2. Підписатися на потрібні джерела через офіційний клієнт.
  3. Створити канали для зведень або додати цей акаунт до наявних.
  4. Надати право публікації, але не зайві адміністративні права.
  5. Отримати власні api_id та api_hash у розділі API development tools
     на my.telegram.org відповідно до офіційної процедури. [Д3]

Первинний login виконувати інтерактивно через CLI: номер, код Telegram і,
за потреби, пароль 2FA. Не закладати припущення, що код обов'язково прийде SMS.
Не зберігати пароль 2FA або код підтвердження в конфігурації чи логах.

Після входу зберігати session-файл на постійному томі /session. Він містить авторизаційні
дані, достатні для повторного доступу без нового коду; його компрометація
небезпечна незалежно від того, чи прихований api_hash. [Д6]

Кожен запуск перевіряє:
  • чи сесія дійсна та належить очікуваному account_id;
  • чи це user-акаунт, а не bot account;
  • чи доступні налаштовані джерела;
  • чи destination є каналом і акаунт може публікувати;
  • чи destination не змінив власну ідентичність через зміну username.

Після відкликання сесії перейти в стан AUTH_REQUIRED. Не повторювати login
безконтрольно та не надсилати запити на коди кожні кілька секунд.

Не запускати два клієнти, які одночасно відкривають один session-файл.
Офлайн-команда login і основний worker повинні використовувати спільний
ексклюзивний process lock у /state, незалежно від режиму підключення.

Telegram попереджає про спостереження за неофіційними API-клієнтами та санкції
за зловживання. Окремий акаунт і низька частота запитів не гарантують відсутності
обмежень або блокування. [Д3]

Технічний session-файл бібліотеки може сам бути SQLite-файлом. Вимога «у БД
тільки опубліковані повідомлення» стосується контентної БД NewsDigest; вона не
означає видалення потрібної авторизаційної сесії. Не записувати у session
новинні тексти власним кодом і не використовувати його як обхід цього обмеження.
login, dialogs і doctor не повинні запускати фонове сканування джерел.

==============================================================================
06. ДЖЕРЕЛА, СПИСКИ ТА ФОРМАТ ІДЕНТИФІКАТОРІВ
==============================================================================

Конфігурація має два рівні:
  sources — загальний реєстр каналів із зрозумілими локальними ключами;
  profiles — тематичні списки, які посилаються на ці ключі.

Наприклад, джерело ua_official має ref каналу, а профіль ukraine містить
source_ids: [ua_official, ua_media]. Щоб додати тему, достатньо додати новий
профіль, його destination і source_ids.

Підтримувані значення ref:
  @example_channel
  https://t.me/example_channel
  -1001234567890

Для числового ID приймати ціле число або рядок зі знаковим десятковим числом.
Внутрішній ідентифікатор — стабільна пара типу peer і ID; зовнішній від'ємний
marked ID нормалізувати засобами бібліотеки, а не ручним обрізанням цифр.

У Telegram одного числового ID може бути недостатньо для API-запитів: потрібен
також відповідний access_hash. Telethon отримує й кешує його після знайомства
з entity, наприклад під час завантаження діалогів. Не переносити access_hash
між акаунтами. Команда dialogs повинна показувати придатні для конфігурації
ID каналів, до яких поточний акаунт уже має доступ. [Д7]

URL конкретного допису, invite link, група обговорення та URL каналу — різні
сутності. У першій версії ref приймає лише username/URL самого каналу або ID.
Для приватного каналу власник спочатку вступає вручну, потім копіює ID із dialogs.
Непідтримуваний URL не перетворювати мовчки на інший канал.

Resolver повинен:
  • перевірити, що джерело є broadcast-каналом, а не особистим чатом;
  • нормалізувати URL та username;
  • звести aliases одного peer до єдиного збору;
  • закріпити resolved peer ID після першого підтвердження;
  • зберігати назву й поточний username як змінні атрибути.

Якщо username надалі вказує на інший peer, потрібне підтвердження власника.
Не переключатися автоматично, особливо для destination.

Якщо кілька source_id посилаються на той самий peer, звести їх до одного
канонічного джерела. Суперечливі дозволи — помилка налаштування або застосування
суворішого обмеження, але не можливість обійти blocked через інший alias.
У межах одного профілю повтори того самого peer не збільшують coverage.

Читати лише об'єднання джерел активних профілів. Не читати всі підписки,
особисті чати, Saved Messages або історію контактів як новинні джерела.
Власні канали призначення заборонено додавати як джерела, щоб уникнути циклів.

ПОРЯДОК ДЖЕРЕЛ Є ЧАСТИНОЮ КОНТРАКТУ:
  profiles.ukraine.source_ids: [ua_official, ua_media, ua_other]
  Якщо подію знайдено тільки в ua_media і ua_other, посилання буде на ua_media.
  Якщо її також використано з ua_official, посилання буде на ua_official,
  навіть коли він опублікував допис пізніше за інші канали.

Не сортувати source_ids за алфавітом, global priority або порядком YAML sources.
За aliases одного peer зберігати найранішу позицію в списку цього профілю.
Один peer у різних профілях може мати різну позицію. Для відкритого вікна порядок
фіксується в config snapshot; reload впливає лише на наступне вікно.

sources.<id>.display_name — необов'язкова точна назва для показу; за null
використовувати title каналу, отриманий із Telegram на момент сканування.
Модель не вигадує назву. За відсутності title допустимий перевірений @username;
без коректної назви/ідентичності джерело не використовується як видиме посилання.

==============================================================================
07. ЧАСОВІ ВІКНА, РОЗКЛАД І ТОЧНІСТЬ ПУБЛІКАЦІЇ
==============================================================================

7.1. Незалежний розклад кожного профілю

Профіль має effective schedule: глобальний schedule_defaults із перевизначеннями
profiles.<id>.schedule. Години, кількість випусків, часова зона й допустиме
запізнення можуть відрізнятися. Відсутність overrides означає успадкування,
а не необхідність копіювати один спільний розклад у код усіх профілів.

Незалежність повинна працювати вже в MVP. На старті дозволено використовувати
однакові 08:00/21:00 для всіх профілів; подальша зміна лише одного профілю не
змінює решту. Наведені нижче інші години — демонстрація можливості.

Підтримати два типи trigger:
  daily_slots:
    довільний непорожній список локальних годин HH:MM щодоби;
    наприклад ["08:00", "21:00"], ["09:00", "15:00", "23:00"] або ["20:00"].
  fixed_interval:
    позитивний every_seconds та anchor_at із явним UTC offset;
    наприклад 21600 секунд від 2026-11-10T00:00:00+02:00 — кожні 6 годин.

Для fixed_interval планові межі: anchor_utc + k * every_seconds, k — ціле
число. Математична сітка існує в обидва боки від anchor; активація профілю
окремо обмежує, які випуски створювати. Restart не пересуває anchor.
Інтервал вимірюється у реальних секундах UTC. Якщо потрібні незмінні місцеві
години, використовувати daily_slots: під час зміни UTC offset fixed_interval
може зсунутися відносно локального годинника.

У першій версії window.mode = between_scheduled_boundaries: кожен випуск
охоплює час від попередньої планової межі профілю до поточної. Окремі довільні
lookback-вікна, cron-вирази й винятки за днями тижня не входять до MVP;
не імітувати їх мовчазним ігноруванням непідтримуваного параметра.

7.2. Межі інформаційного вікна

Для впорядкованих планових меж конкретного профілю B0, B1, B2, ...:
  випуск із межею Bi → [B(i-1), Bi);
  start включений, end виключений;
  start_utc <= message.date < end_utc.

Час отримання повідомлення сервером не замінює час публікації у Telegram.
Не використовувати «08:00:01», «21:00 плюс секунда» або включення обох меж.
Повідомлення на межі належить наступному вікну цього ж профілю.
Перетин вікон РІЗНИХ профілів дозволений і є нормальною поведінкою.

Приклад «Україна», Europe/Kyiv, 08:00/21:00:
  випуск D 08:00 → [D-1 21:00, D 08:00);
  випуск D 21:00 → [D 08:00, D 21:00).
  07:59:59 → ранковий; 08:00:00 → вечірній;
  20:59:59 → вечірній; 21:00:00 → наступний ранковий.

Приклад «Криптовалюти», Europe/Kyiv, 09:00/15:00/23:00:
  випуск D 09:00 → [D-1 23:00, D 09:00);
  випуск D 15:00 → [D 09:00, D 15:00);
  випуск D 23:00 → [D 15:00, D 23:00).

Приклад один випуск о 20:00:
  [D-1 20:00, D 20:00), а не автоматично «поточна календарна доба».
За fixed_interval кожні 6 годин: сусідні межі відрізняються на 21600 секунд.

Перевірка часу scheduler та сканування — різні операції. Сканування джерел
прив'язане до належного випуску профілю: окремого фонового інтервалу збору немає.
Пауза між сторінками API й обмежений retry не є новим розкладом публікацій.

7.3. Часові зони та перехід годинника

За замовчуванням schedule.timezone = Europe/Kyiv, але кожен профіль може
перевизначити її, наприклад на UTC. app.timezone — окреме налаштування
для загальних календарних бюджетів/операцій, а не примусовий timezone профілів.
У БД усі моменти зберігати як timezone-aware UTC timestamps.
Для локальних слотів використовувати zoneinfo й актуальну IANA timezone database,
а не жорсткий UTC+2/UTC+3. [Д8]

daily_slots: спочатку побудувати локальні календарні межі, потім перевести в UTC.
Не віднімати фіксовані 11/13/24 години від кінця. На зміні UTC offset тривалість
локальної доби або нічного вікна може бути іншою.

Явні політики DST, однакові defaults із можливістю налаштування профілю:
  ambiguous_time: first_occurrence — один запуск на першій появі локального часу;
  nonexistent_time: shift_forward — перенести межу на першу валідну локальну
    хвилину після пропущеного часу; зафіксувати перенесення в аудиті.
Якщо кілька слотів після такого перенесення мають один UTC instant, створити
одну межу, не нульові вікна й не кілька однакових постів. Зафіксувати злиття.
Уже збережені UTC-межі не перераховувати після оновлення tzdata.

7.4. Активація, restart і виконання

Стан у службових файлах /state вести окремо для профілю:
schedule_activation_at, schedule_revision, last_materialized_boundary_utc,
next_boundary_utc і last_sent_run_id.
Остання успішна публікація — НЕ розрахунковий початок наступного вікна.

Під час першої активації запланувати найближчу майбутню межу. Початок її вікна —
попередня межа сітки цього профілю. Доступну історію читати лише тоді, коли
настане ця майбутня межа. Перший запуск/активація не запускає негайний backfill.
Історичні випуски до активації не створювати автоматично. Якщо заплановане
сканування не завершене, показати partial, а не «новин немає».

Після restart відновлювати планові вікна, належні після збереженої активації,
з урахуванням історичних schedule revisions. Запуск о 08:12 для слоту 08:00
обробляє лише вікно до 08:00. Час збою не зсуває решту випусків.

Одночасні межі різних профілів дозволені. Створення due-run — незалежне й
атомарне; загальні мережеві квоти не повинні змішувати їхні вхідні дані.
Сусідні випуски одного профілю обробляти/публікувати у хронологічному порядку
із per-profile lock; published-memory читається з підтверджених публікацій БД.
Якщо новіший уже вийшов, старіший
автоматично не надсилати; skipped + alert, ручне рішення окремо.

7.5. Межа даних та фактична публікація

Кожна планова межа — cutoff даних і ПОЧАТОК сканування для цього випуску.
Типові значення, які профіль може перевизначити:
  scan_target_seconds = 60;
  publication_target_delay_seconds = 180;
  run_timeout_seconds = 600;
  misfire_grace_seconds = 10800.

180 секунд — проєктна ціль за справних залежностей і перевіреного навантаження,
а не гарантія швидкості GPT-5.6 Sol або Telegram. Затримка не розширює вікно.
Не читати та не обробляти майбутній випуск до cutoff. Сканування, черга,
AI-обробка й надсилання входять у спільну ціль 180 секунд. scan_target_seconds —
ціль, не дозвіл відкинути непереглянутий хвіст. run_timeout_seconds обмежує
тривалість активної спроби від її фактичного початку; перевищення цілі публікації
фіксується як запізнення, а перевищення timeout — як невдале/неповне виконання.
Мережеві обмеження можуть зробити ціль недосяжною; перевірити її на стенді.

Не гарантувати одночасно повні дані до нульової секунди й доставку рівно в неї.
Не надсилати порожню заглушку заради формальної точності. Для щільних розкладів
валідація попереджає, якщо цільова обробка не вкладається між межами; потрібні
навантажувальний тест, обмежена черга й явна політика застарілих запусків.

7.6. Зміна розкладу без пропусків та повторів

reload-config не перерізає вже відкрите вікно. Для кожного зміненого профілю:
  1. Обчислити C — кінець поточного відкритого вікна за СТАРИМ розкладом.
  2. Поточне вікно завершується на C зі своїм snapshot.
  3. Новій schedule revision задати effective_from = C.
  4. Обчислити N — першу межу НОВОГО розкладу строго після C.
  5. Створити перехідне вікно [C,N), навіть якщо C не є слотом нової сітки.
  6. Наступні вікна — між сусідніми межами нового розкладу.

Приклад: заміна 08:00/21:00 на 09:00/23:00 під час денного вікна.
Чинне вікно завершується о 21:00; перехідне — 21:00–23:00; далі —
23:00–09:00. Не пересувати початок перехідного вікна назад на 09:00.
Зміна timezone чи типу trigger застосовується за тим самим алгоритмом.

Зберігати стару й нову revisions, C, N та автора зміни. Ще не виконані майбутні
запуски старої revision після C не виконувати; підготовлені кешовані чернетки таких запусків скасувати з технічним аудитом,
але не змінювати підтверджені публікації БД або sending/uncertain guards.
Якщо кандидат створює конфлікт із уже надісланим/невизначеним випуском,
відхилити автоматичне застосування й вимагати розв'язання конфлікту.
Повторна зміна до C замінює лише pending revision атомарно, з історією аудиту.
Зміна глобальних defaults обробляється окремо для кожного профілю, якого
вона реально торкається. Власні overrides інших профілів залишаються чинними.

При вимкненні профілю не створювати нових випусків. Після повторного ввімкнення
за замовчуванням продовжити з найближчої майбутньої межі; її вікно сканувати
лише після настання цієї межі;
пауза явно залишається в журналі, без лавини історичних постів.
Не плутати адміністративне вимкнення з аварійним restart активного профілю.

Технічні правила розкладу, skipped-межі й pending revisions — у /state,
не у таблицях контентної БД. У БД відповідна revision з'являється лише як
metadata фактично опублікованого поста. Перевірка guard/reconciliation власного
каналу після збою допускається поза слотом: це захист доставки, не збір новин.

08. СКАНУВАННЯ ЗА РОЗКЛАДОМ І ТИМЧАСОВИЙ КЕШ
==============================================================================

8.1. Коли і що читати

Сканер запускається для due-run на плановій межі профілю. Він отримує history
лише джерел зі snapshot цього профілю і лише для його [start,end).
Пагінація історії доступна через messages.getHistory; API повертає записи
за спаданням дати. Параметри offsets і точні межі перевіряти тестами. [Д9]

Приклад: о 08:00 профіль ukraine починає читати пости від учора 21:00 до
сьогодні 08:00. Пости рівно о 08:00 та пізніші не потрапляють у цей випуск,
навіть якщо сканер фактично читає канал о 08:01. Публікація — після обробки.

Заборонено:
  • постійні handlers для накопичення новин;
  • незалежний 300-секундний history polling;
  • читання історії всіх підписок або всіх каналів при запуску контейнера;
  • початок «від останнього записаного source-поста» замість меж цього вікна;
  • обмеження останніми 100 постами без перевірки всього потрібного діапазону.

Перший запуск тільки реєструє активацію/наступну межу. Після аварії дозволено
відновити активний run або належний misfire у межах його політики. Це завершення
конкретного запланованого випуску, а не перехід до постійного сканування.
Ручний preview запускається лише явною CLI-командою із профілем і вікном.

8.2. Пагінація й дані кешу

Отримувати сторінки, доки не досягнуто start або кінця доступної історії.
У кожній сторінці додатково фільтрувати start <= message.date < end.
У кеші унікальність — (source_peer_id, telegram_message_id, version_hash).
Копії в різних каналах не видаляти як походження: вони потрібні для злиття
і вибору видимого джерела за source_ids.

Тимчасові поля:
  peer_id, message_id, date_utc, edit_date_utc, fetched_at_utc, raw_text,
  normalized_text, text_hash, grouped_id, forward_origin, entity_links,
  media_type, observed_title, observed_username, version_hash, source_id.
Жоден із raw/normalized/evidence-текстів не копіюється в published.sqlite3.

Cursor, перевірений діапазон і coverage зберігати в manifest активного кешу.
Спочатку атомарно записати сторінку, потім пересунути cursor; не навпаки.
Після crash продовжити run або повторно просканувати його діапазон без
подвоєння кешованих записів. Пропуски message_id самі по собі не є помилкою.

8.3. Спільні джерела і повнота

У межах одного scheduler tick належні runs можуть мати спільний scan batch.
Для спільного peer прочитати об'єднання потрібних інтервалів; кожен run має
власні фільтри, порядок джерел і coverage. Не позначати довге вікно complete
лише через успішне коротке сканування. Не чекати майбутнього слоту іншого профілю
заради об'єднання запитів. Кеш минулого завершеного випуску не є джерелом новин.

Статуси тимчасового coverage:
  complete — весь доступний API-діапазон цього джерела переглянуто;
  partial — пагінація/перевірка діапазону не завершена;
  unavailable — немає доступу або відповіді;
  excluded — заборонено правилами/правами.
complete не означає відновлення раніше видалених постів чи історичних редакцій.
Нуль отриманих постів не є сам по собі доказом повного сканування.

Початкові локальні обмеження: один Telegram history request одночасно,
пауза щонайменше 1000 мс між запитами, коригування за FloodWait.
Це параметри застосунку, не обіцянка безпечної квоти Telegram.

Після сканування зафіксувати input snapshot у кеші: часові межі, перелік
версій, порядок джерел, права і coverage. Сканування не є атомарним snapshot
усієї платформи: джерело може змінитися під час перегляду сторінок.

8.4. Життєвий цикл тимчасового кешу

За замовчуванням файловий кеш у /cache, TTL=86400 секунд від створення run.
Параметр configurable; TTL не подовжується нескінченно від кожного читання.
Кеш переживає звичайний restart контейнера, але не є постійним архівом і
не включається в backup. RAM-only режим не є базовим через відновлення збоїв.

Успіх: підтверджено пост → зафіксовано його в БД → звільнено cache references
→ видалено непотрібні raw, candidates, evidence fragments і AI drafts.
Shared cache видаляється, коли закінчили всі поточні runs-споживачі.
Не тримати його до наступного майбутнього випуску «про всяк випадок».

Preview: результат показати/повернути, кеш прибрати після завершення;
технічний збій: кеш дозволено зберігати до retry або TTL, що настане раніше.
TTL expired: видалити контент, позначити cache_expired. Для ще допустимого run
без спроби відправки можна повторити сканування. Після sending/uncertain
спершу reconciliation; нова генерація/відправка заборонена до з'ясування.

На TTL незавершеного run спочатку зупинити його обробку; не видаляти файли
з-під активного читача без контрольованого завершення. При невизначеній
доставці зберігається лише мінімальний guard без тексту, див. розділ 14.
Задати max_cache_size_mb, початково 512: при переповненні очистити лише
прострочений/звільнений кеш; якщо місця все ще немає — явна помилка, не
видалення даних активного run і не приховане перенесення raw у БД.

==============================================================================
09. РЕДАГУВАННЯ, ВИДАЛЕННЯ, МЕДІА ТА ЗАПІЗНІЛІ ДАНІ
==============================================================================

Через сканування лише на межах застосунок бачить доступний стан повідомлень
на момент читання, а не повну історію їхнього існування. Цю властивість не
маскувати обіцянкою «усіх постів, що будь-коли існували у вікні».

Редагування:
  • edit_date < window_end — можна використовувати отриману редакцію;
  • edit_date >= window_end із новим змістом — не видавати її за відому до cutoff;
  • за наявності дозволеної версії до cutoff у кеші цього scan batch можна
    використати її; інакше post_cutoff_edit → виключення/needs_review;
  • точну історичну редакцію, яку ніколи не спостерігали, не відновлювати з уяви;
  • редагування старого допису саме по собі не робить його публікацією нового вікна.
Для рівності edit_date=cutoff застосовується виключена верхня межа: редакція
вважається зробленою вже після завершення інформаційного вікна.

Видалення:
  • допис, видалений до першого планового сканування, може залишитися невідомим;
  • відсутність у випадковій сторінці історії не доводить видалення;
  • у межах активного job можна перевірити вибрані для посилань message IDs;
    підтверджено видалений/недоступний допис не використовувати як єдину опору;
  • за потреби переобрати доступне джерело за тим самим source_ids порядком
    до підготовки фінального payload; після початку відправки — правила розділу 14.

Після публікації немає фонового моніторингу старих джерел на редагування/
видалення. Виявлене під час наступного належного сканування або ручної перевірки
суттєве спростування потребує оновлення у наступному випуску чи підтвердженого
редагування власного поста. Не створювати автоматичні позапланові повідомлення.

Медіа: працювати з текстом і підписами. Альбом grouped_id об'єднувати в один
логічний матеріал, не захоплюючи підписи з повідомлень за межами [start,end).
Без тексту — media_only; OCR, транскрипція, аналіз відео й скачування медіа
не входять до MVP. URL без змістовного тексту не перетворювати на вигаданий
переказ зовнішньої статті. Зовнішній web crawling не виконується.

Пізно доступний допис минулого вікна не переносити мовчки в поточне. Якщо його
випадково виявлено під час дозволеної операції, створити технічне сповіщення
без постійного архівування тексту; подальше рішення власника — явне.

==============================================================================
10. ОЧИЩЕННЯ, ТЕМАТИЧНІ ФІЛЬТРИ ТА РЕКЛАМА
==============================================================================

Raw text зберігати незмінним ТІЛЬКИ в тимчасовому кеші run до очищення/TTL.
Normalized text — окреме кешоване представлення для порівняння, не заміна
оригіналу й не запис до контентної БД.

Очищення може прибирати зайві пробіли, повтори оформлення, налаштовані підписи
каналів і рекламні хвости. Не видаляти заперечення, дати, числа, одиниці виміру,
імена, назви активів, місця та посилання, необхідні для розуміння твердження.

Розрізняти:
  • службові повідомлення — не включати;
  • дублікати — зберігати походження, не повторювати в тексті;
  • рекламу, реферальні заклики, розіграші, «підпишись» — фільтрувати;
  • новину зі згадкою реклами/розіграшу — не видаляти лише через одне слово;
  • коротке важливе повідомлення — не відкидати лише через малу довжину.

Фільтри профілю: тема, допустимі категорії, слова-підсилювачі та стоп-правила.
Жорсткі виключення застосовувати до змісту з урахуванням контексту або як
чітко налаштовані патерни. У rule_based режимі невпевнений випадок залишати
кандидатом, а не виконувати агресивне видалення.

Маркери «терміново», кількість emoji, переглядів або репостів не роблять
повідомлення автоматично важливим чи достовірним.

Змішаний канал може бути джерелом кількох профілів. Спочатку обмежити дані
списком source_ids конкретного профілю, потім застосувати його тематичні правила.
Не давати одному профілю прихований доступ до матеріалів іншого.

Причину виключення зберігати лише у тимчасовому manifest машинним кодом: service, ad, duplicate, off_topic,
unsupported_media, rights_blocked, unavailable, low_priority, invalid_content.
У preview показувати кількість записів за кожною причиною.

Після очищення кешу дозволено залишити тільки агреговані лічильники причин
без текстів/масиву всіх вхідних постів. До БД вони потрапляють лише як
узагальнені metadata підтвердженого вихідного зведення.

11. ДЕДУПЛІКАЦІЯ ТА ПАМ’ЯТЬ МІЖ ВИПУСКАМИ
==============================================================================

У МЕЖАХ ВИПУСКУ:
  1. Точні дублікати — hash normalized_text.
  2. Майже однакові — прозорі текстові shingles/Jaccard; початковий поріг 0.85
     калібрується. Числа, місце, час і заперечення не зникають при порівнянні.
  3. Семантична подія — дозволена AI-обробка учасників, дії, місця, часу й об'єкта.
     Рішення LLM перевіряється через message_refs і evidence у кеші.

Не об'єднувати всі пости про Bitcoin або Україну в одну подію. Різні атаки,
різний час чи різні місця — не дублікати тільки через схоже формулювання.
Один live URL може містити кілька подій. Репости не є незалежними підтвердженнями.
Зберігати в кеші походження всіх копій до вибору видимого посилання.

МІЖ ВИПУСКАМИ:
  Пам'ять формується з items_json ВЖЕ ОПУБЛІКОВАНИХ повідомлень цього профілю
  за останні 7 днів (configurable), а не з окремих постійних profile_events,
  message_versions, candidates або raw_messages.
  Поля пам'яті: короткі власні опубліковані формулювання/claims, fingerprint,
  дата/вікно і посилання на власний випуск. Вхідні оригінали не потрібні.

Правила:
  факт уже опубліковано без розвитку → не повторювати;
  з'явився суттєвий новий факт/спростування → пункт «Оновлення: …»;
  раніше подію лише сканували, але не публікували → не вважати її опублікованою;
  preview, помилка доставки або невизначена спроба → пам'ять не оновлюється.

За відсутності старих вихідних текстів через retention/restore система не має
повної історії новин. Не компенсувати це створенням прихованого архіву джерел.
Невизначеність змістового зіставлення — пропуск/review, а не вигаданий факт.

Одна подія може бути релевантною різним профілям. Пам'ять profile-local:
публікація у ukraine не блокує crypto. Посилання в кожному профілі обирається
за ЙОГО порядком source_ids. Змістове злиття і вибір видимого джерела — окремі
операції; перше може використовувати LLM, друге — детермінований код.

У rule_based режимі не заявляти таку саму якість змістового групування,
як у AI-режимі. Проміжні clusters та невикористані facts живуть тільки в кеші.

==============================================================================
12. РЕДАКТОРСЬКІ ПРАВИЛА, ДОСТОВІРНІСТЬ ТА LLM
==============================================================================

12.1. Загальні вимоги до змісту

Кожне фактичне твердження має спиратися на доступний текст конкретного джерела.
Посилання на канал загалом не замінює посилання на допис. Один видимий лінк
після злиття — редакторське правило навігації, не доказ, що обраний канал
підтверджує всі додаткові деталі інших джерел. Див. розділ 13.3.

Не називати всі Telegram-канали «першоджерелами». Першоджерелом вважати лише
встановленого автора/організацію або доступний первинний документ. В інших
випадках писати «Джерело» чи «За повідомленням…».

Кілька каналів, які скопіювали один текст або послалися на одну установу,
не є незалежними підтвердженнями. Зберігати forward_origin і спільний upstream,
коли його можна встановити; невідоме походження не вигадувати.

Заяву, оцінку, прогноз і встановлений факт розрізняти. Непідтверджену важливу
інформацію або пропустити, або явно атрибутувати. За суперечливих даних не
вибирати «правильну цифру» за кількістю повторів і не усереднювати її.

Не додавати причин, наслідків чи деталей із пам'яті LLM. Не робити висновок
«ринок упав через X», якщо джерела цього не підтверджують. Стару подію, про яку
сьогодні знову написали, не видавати за подію поточного дня.

Пріоритет подій визначати прозоро: налаштований редакторський пріоритет,
відповідність темі, новизна, суспільна/тематична значущість, доступність
первинного підтвердження. Початкові ваги підбирати на контрольній добірці.
source_priority — редакторська настройка, а не «відсоток правдивості».

Для криптопрофілю: новини, регулювання, біржі, безпека, інфраструктура та
значущі ринкові події. Без сигналів купівлі/продажу, автоматичних угод,
обіцянок прибутку чи доступу до біржових ключів. Ціни з постів — історичні
значення на час джерела, а не гарантовано поточний курс.

12.2. Режим rule_based

Відбір за правилами, точна/наближена дедуплікація, короткі дозволені фрагменти
або заголовки з атрибуцією та посиланнями. Не склеювати шматки різних речень так,
щоб створювався новий зміст. Відсутність ШІ повинна бути видимою в метаданих
випуску й за потреби в його підписі: «Добірка без ШІ-узагальнення».

12.3. Режим ai_grounded

Мета — короткий природний український текст та змістове об'єднання. Увімкнення
потребує налаштованого провайдера, моделі, бюджету і чинного дозволу для КОЖНОГО
тексту, який увійде у запит. Дозвіл перевіряти до будь-якого AI-виклику.

Інтерфейс LLMProvider:
  classify_and_extract(messages, profile_rules) → structured candidates;
  group_events(candidates, published_context) → structured events;
  compose_digest(events, limits) → structured digest;
  usage() → фактичні token/витратні показники, коли провайдер їх надає.

Для цього проєкту обрано provider=openai та model=gpt-5.6-sol.
Усі AI-стадії MVP використовують цю модель; не підміняти класифікацію або
генерацію дешевшою/іншою моделлю без явного погодження. Бізнес-логіку відділити
від OpenAIProvider; інші провайдери й локальна LLM не є обов'язковими роботами.
Зміна моделі можлива через конфігурацію після перевірки сумісності й якості.
Значення model=null і «провайдер обирається пізніше» більше не є вимогами ТЗ.

Для великої кількості дописів обробляти пачками. Спочатку зібрати структуровані
факти по пачках, потім виконати міжпачкове групування. Не обрізати мовчки перші
N повідомлень і не називати результат оглядом усіх джерел. Якщо бюджет змушує
відібрати підмножину, враховувати різні джерела, час і пріоритет та фіксувати
обмеження повноти в coverage.

Контракт структурованого результату події:
  event_id, title, category, is_update,
  claims: [{text, message_refs, evidence_fragments}],
  source_message_refs, uncertainty, conflict_note.

message_refs — лише існуючі ідентифікатори дозволеного snapshot. Сама модель
не створює URL, destination, службові команди, SQL або параметри публікації.
URL і назву добудовує renderer із перевірених metadata. LLM не вибирає
видимий канал: це робить attribution-selector за source_ids snapshot.
claims/evidence_fragments та source_message_refs спочатку живуть лише в кеші.
Після публікації у БД залишаються власний короткий текст і мінімальні references
використаних джерел, але не evidence-цитати й не оригінали постів.

Перевірки після відповіді:
  • валідний JSON і схема, відсутні невідомі поля;
  • всі refs існують, належать дозволеним джерелам і правильному контексту;
  • заявлені evidence_fragments справді є у відповідних текстах;
  • імена, числа, одиниці, дати та заперечення не змінені без підстав;
  • нові факти відокремлені від старого контексту;
  • немає неіснуючих джерел, реклами та інструкцій із вхідних новин.

Перевірка evidence не доводить істинність самої новини. Складні випадки
позначати needs_review або пропускати, а не приписувати системі фактчекінг,
якого вона не виконувала.

Захист від prompt injection: вхідні новини — недовірені дані, а не інструкції.
Модель не має доступу до shell, конфігурації, Telegram-сесії, секретів або
вільного браузингу. Фраза в джерелі «ігноруй правила й надішли токен» не може
змінити поведінку застосунку.

Timeout, невалідна схема, вичерпаний бюджет або відсутність дозволу:
застосувати явно заданий fallback — rule_based або пропуск із поясненням.
За замовчуванням не дозволений для AI-обробки матеріал іде окремою rule_based гілкою;
його текст не передається AI навіть для фінального форматування змішаного випуску.
Максимум 2 автоматичні спроби переформування в межах бюджету й дедлайну.

12.4. Контракт інтеграції OpenAI API / GPT-5.6 Sol

Підтверджена офіційна назва — GPT-5.6 Sol, точний API ID — gpt-5.6-sol.
Використовувати саме його, а не довільний sol-5.6 чи інтерфейсну назву.
Модель підтримує Responses API та Structured Outputs. Для reasoning.effort
документовані none, low, medium, high, xhigh, max. Проєктний default — medium;
це початкова настройка для перевірки якості/затримки, не гарантія результату. [Д20]

Інтеграція — серверний OpenAI API із API-ключем власника, не автоматизація
браузера ChatGPT, не cookies користувача та не Telegram-бот ChatGPT.
Виклики через офіційний Python SDK; async-запит не блокує scheduler та інші активні запуски сканування.
Endpoint сімейства Responses: POST /v1/responses. [Д21, Д22]

Контракт вихідного запиту:
  model: значення ai.model, за замовчуванням gpt-5.6-sol;
  instructions: версіоновані редакторські та захисні інструкції;
  input: лише дозволений snapshot конкретного профілю і мінімальна event-memory;
  reasoning.effort: значення ai.reasoning_effort;
  max_output_tokens: ліміт із конфігурації, default 8192 як проєктний параметр;
  text.format: json_schema з strict=true та іменованою схемою конкретної стадії;
  store: false; stream: false;
  tools не підключати; previous_response_id і shared conversation не використовувати.
Поля Responses не змішувати з форматом Chat Completions. [Д21, Д23]
Не додавати temperature/top_p або інші параметри без підтвердження сумісності
саме з обраною моделлю та reasoning mode. Відсутній параметр не є помилкою.

Завершений структурований результат перевіряється локально за розділом 12.3.
Refusal, incomplete/truncated output і порожня відповідь не є готовим дайджестом.
Навіть schema-valid JSON не гарантує правдивості фактів. Внутрішні reasoning
повідомлення не публікувати; renderer отримує лише валідовані редакторські дані.
Structured Outputs та обробка відмов/незавершених відповідей описані в [Д23].

До першої production-публікації виконати перевірку доступності ai.model
для налаштованого API-проєкту через Models API та короткий явно запущений
синтетичний probe. Саме існування моделі в каталозі не доводить, що конкретний
ключ має доступ і достатню квоту. Список доступних моделей надає GET /v1/models. [Д24]
Не виконувати платний probe у кожному healthcheck або кожні 5 секунд.

Немає ключа/доступу, неправильна модель або параметр: позначити AI_NOT_READY,
дати діагностичну причину; не переходити приховано на іншу модель.
Тимчасові rate limit/мережеві/серверні помилки — обмежений retry з backoff;
помилки авторизації, конфігурації й вичерпаної квоти — без сліпого retry-loop.
Розрізняти 429 rate_limit та недостатню квоту/баланс за кодом помилки. [Д25]
Єдиний контролер спроб враховує retries SDK, repair-запити, бюджет і дедлайн.
Не допускати множення «2 спроби SDK × 2 pipeline × 2 scheduler».

Кешувати лише перевірений результат у ТИМЧАСОВОМУ кеші; ключ включає profile_id,
source_order_hash, attribution/format version, model,
reasoning_effort, prompt/schema version, права, input snapshot та hash
published-context. Враховувати фактично повернений model у метаданих.
Після невизначеного API timeout витрата може залишатися невідомою:
не позначати її автоматично нульовою, резерв зберігати до узгодження.
Повторний LLM-запит може збільшити витрати, навіть якщо Telegram-пост один.

store=false не означає автоматично Zero Data Retention і не скасовує
застосовні правила зберігання/моніторингу OpenAI. Перевірити їх для проєкту;
не обіцяти, що дані гарантовано ніде не зберігаються. [Д27]

API має окремий від ChatGPT облік і білінг; перевірити доступний баланс/кредити
саме API-організації. Наявність підписки ChatGPT сама по собі не налаштовує
цей серверний API-проєкт і його платіжні/технічні ліміти. [Д26]

12.5. Життєвий цикл AI-даних

Requests, responses, evidence fragments та неопубліковані summaries не
зберігати в контентній БД або звичайних логах. Їхній локальний кеш очищається
за правилами розділу 8.4. Контроль якості виконується ДО очищення. Після нього
повний текстовий аудит джерел неможливий без окремого повторного доступу до них;
це свідомий наслідок вимоги не архівувати вхідні пости.
Службовий облік невдалих/preview викликів — лише числові usage/budget metadata
без контенту, у /state. Метадані успішного run можна долучити до його публікації.

==============================================================================
13. ФОРМАТ ОДНОГО ЗВЕДЕННЯ
==============================================================================

13.1. Обов'язковий вигляд пункту

  Короткий зміст новини — Назва каналу

Назва каналу є клікабельним текстом; адреса веде на конкретний вхідний допис.
Не показувати сирий URL, окремий рядок «Джерело», посилання на головну каналу
або список із кількох каналів після одного пункту. На одну новину — один
видимий source-link. Telegram підтримує text URL entities. [Д10, Д12, Д29]

Умовний макет, НЕ реальні новини:

  УКРАЇНА · ЗВЕДЕННЯ НА 08:00
  Період: 09.11 21:00 — 10.11 08:00, Київ

  1. Коротко: що сталося, де та яка найважливіша деталь. — Канал А

  2. Оновлення: що змінилося у раніше описаній події. — Канал Б

  #ukraine_20261110T060000Z

У макеті TXT назви — звичайний текст. У Telegram вони мають MessageEntityTextUrl
на перевірений URL допису. Видима частина «Канал А» веде, наприклад, на
https://t.me/example_channel_a/12345 (лише демонстраційна адреса).

Один пункт — один компактний абзац, 1–2 короткі речення. Окремий великий
заголовок для кожної новини не потрібний. За замовчуванням нумерація і порожній
рядок між пунктами. Не додавати редакторського вступу або переказу всього випуску.
Назва випуску береться з профілю й фактичного часу, не лише «ранковий/вечірній».

13.2. Вибір одного видимого каналу

Вхід: ordered source_ids із snapshot профілю та підтверджені учасники події.
  1. Сформувати eligible participants: дозволені, реальні, доступні дописи
     з потрібного вікна, які стосуються саме цієї події й не відкинуті як реклама,
     вигадане походження, підтверджено видалений/спростований матеріал тощо.
  2. Пройти source_ids ЗВЕРХУ ВНИЗ. Вибрати перший peer із цього набору.
  3. Усередині обраного каналу вибрати latest_relevant: найновіший придатний
     допис цієї події, що підтримує її основне твердження; при рівних датах —
     найбільший message_id. Не підставляти будь-який останній допис каналу.
  4. Взяти назву з display_name або зафіксованого Telegram title, збудувати
     конкретний message URL; не доручати це LLM.
  5. Решту використаних source/message refs залишити внутрішніми metadata
     відповідного пункту. Після публікації можна зберегти ці ID/URL, але не raw.

Порядок source_ids має пріоритет над source.priority, оцінкою популярності,
часом першого повідомлення про подію та порядком відповіді LLM.
Канал, який перший у конфігу, але не писав про цю подію, не є кандидатом.
Для aliases одного peer використовується найраніша позиція профілю.
Порядок пунктів зведення визначається важливістю, не порядком каналів.

Якщо вибраний допис підтверджено недоступний до відправки, прибрати його
з eligible й повторити алгоритм. Не змінювати вже відправлений payload на retry.
Немає придатного конкретного посилання → пункт needs_review/пропуск із
технічною причиною, а не фіктивне джерело. У публічний канал не публікувати
приватний source-link за замовчуванням; дозволи не обходити порядком списку.

13.3. Злиття змісту не повинне спотворювати атрибуцію

Для однакових копій достатньо одного спільного короткого викладу.
Для різних доповнень можна використати кілька дозволених джерел, але кожний
claim перевіряється за його фактичними evidence у кеші. Перший у конфігу канал
не стає через це «першоджерелом», найнадійнішим або автором усіх подробиць.

Якщо істотна додаткова деталь є тільки в іншому каналі, її потрібно коротко
атрибутувати в самому реченні («за повідомленням Каналу Б, …») без другого
посилання або не включати. Не приписувати її Каналу А. Якщо компактно й точно
сформулювати неможливо або джерела суперечать одне одному — needs_review,
а не вибір «правильної» цифри за позицією у конфігу.

Обмеження «один лінк» стосується тільки відображення, НЕ кількості дозволених
джерел для перевірки фактів. Старий max_sources_per_event=2 не застосовується
як обмеження provenance; усі реально використані references залишаються відомі.

13.4. Довжина, форматування й відбір

Початкові defaults: Україна до 8 подій, крипто до 6, max_chars=3500,
summary_max_sentences=2, item_style=numbered, visible_links_per_item=1.
Звичайний вихідний текст — український; усі обов'язкові застереження й
атрибуції входять у ліміт речень/довжини. Це робочі налаштування, не квоти API.

Платформний message_length_max перевіряти в Telegram config. Ліміт описаний
у Unicode code points; offsets/lengths entities рахуються у UTF-16. [Д11, Д12]
Перевага реалізації — plain text + явні entities; не вставляти довільний HTML
з джерел. У назві прибрати переноси/керувальні символи, не змінюючи ідентичності
каналу. Не вирізати emoji так, щоб зламати offsets. URL preview вимкнути.

Після рендерингу перевірити весь текст разом із header, тире, назвами й footer.
Завеликий випуск → скоротити формулювання, потім прибрати менш важливі події,
повторити перевірку. Не різати посилання/заперечення й не ділити на кілька постів.
Подію, прибрану з фінального тексту, не вважати опублікованою в event-memory.

Робоче тлумачення «кожного поста» — кожного відібраного пункту. Відбір головного
залишено до уточнення власника. Публікація ВСІХ унікальних новин без верхньої
межі може конфліктувати з вимогою одного повідомлення; це потребує окремого
рішення, не прихованого розбиття на кілька постів або мовчазної втрати новин.

Коли важливих новин немає при достатньому coverage — короткий статус.
Коли сканування неповне — позначка неповноти, не «новин немає».
Технічні статусні випуски також є власними публікаціями: вони потрапляють у БД
після доставки, але не потребують вигаданого новинного посилання.

==============================================================================
14. ПУБЛІКАЦІЯ, ПІДТВЕРДЖЕННЯ ТА ЗАХИСТ ВІД ПОВТОРІВ
==============================================================================

14.1. Ідентичність випуску й розміщення стану

  digest_key = profile_id + window_start_utc + window_end_utc
  marker = profile_id + UTC-межа + за потреби короткий hash ключа.
Номер config/schedule revision не робить той самий інтервал новим випуском.
Один worker/process lock, per-profile lock і файл guard захищають від гонок;
UNIQUE у published_messages — останній захист після підтвердження доставки.

БД не має таблиці pending outbox/runs. До публікації:
  /cache/runs/<key>/outgoing.json — тимчасові text, entities, random_id,
    destination, marker, payload_hash та потрібні metadata майбутнього поста;
  /state/delivery_guards.json — тільки key, destination, marker, payload_hash,
    random_id, фаза/час і, коли відомо, message_id; БЕЗ text/raw/prompt/evidence.

Мінімальний guard — технічний захист, не запис опублікованого повідомлення.
Його не переносити до БД до підтвердження. TTL кешу не видаляє unresolved guard.
У ньому після TTL немає джерельних текстів чи чернеток.

14.2. Послідовність надсилання

  1. Перевірити published_messages: уже опублікований key → не надсилати.
  2. Перевірити guard: sending/uncertain → reconciliation, не нова генерація.
  3. Підготувати й валідовувати текст; записати outgoing.json атомарно.
  4. Створити випадковий 64-бітний random_id один раз, зберегти його у payload
     і guard; перед мережевим викликом guard переходить у sending.
  5. Лише після durable-запису payload і guard виконати messages.sendMessage.
  6. Отримати підтвердження з конкретним destination_message_id; зберегти
     короткий receipt у кеші/guard, щоб пережити помилку запису БД.
  7. В одній SQLite-транзакції вставити/ідемпотентно підтвердити опублікований
     пост і ТІЛЬКИ його metadata. Власні опубліковані claims стають пам'яттю.
  8. Позначити завершення у службовому стані; звільнити/очистити кеш.

MTProto random_id призначений для запобігання повторному надсиланню. Зберігати
й повторно використовувати той самий ID для того самого незмінного payload;
не дозволяти helper-методу генерувати новий ID на кожній спробі. [Д4]
Не припускати необмеженого строку серверної дедуплікації: потрібен reconciliation.

14.3. Telegram прийняв, але відповідь/запис БД втрачено

Не додавати у БД запис «можливо опубліковано» і не надсилати заново сліпо.
Перевірити own destination: знайти marker і перевірити текст/entities або
їхній hash, профіль, часову межу та очікуваний канал. Перегляд історії має
покривати потрібний діапазон; «не знайшли серед останніх 100» не є доказом.

Знайдено точний власний пост → зафіксувати його ID і серверний час у БД як
підтверджений, confirmation_method=reconciled. За втрати source-кешу не
вигадувати provenance/items: відновити тільки доступний вихідний текст,
entities й metadata, metadata_recovery=partial за потреби.

Не вдалося однозначно встановити результат → guard=uncertain, сповіщення
власнику, повторна публікація цього key заблокована. Немає поста у доступній
вибірці — ще не доказ, що він ніколи не був доставлений або не був видалений.
Повторна відправка допустима лише після достовірної діагностики/явного рішення,
з існуючим payload/random_id, якщо вони збережені й це безпечно.

При втраті кешу, але наявному sending/uncertain guard, спочатку reconciliation.
Не сканувати джерела й не формувати інший текст, щоб «відновити» невідому відправку.
Якщо ні guard, ні актуальній БД не можна довіряти після restore — publication hold
до звірки власних каналів. Математичного exactly-once за будь-якого збою не
обіцяти; ціль — не створювати дублі через сліпі retry.

14.4. Властивості й обмеження

Destination, source order, назви/посилання, формат і payload фіксуються до send.
Після початку send звичайний retry їх не змінює. Preview не створює send guard
і не робить insert у published_messages. Ручне підтвердження ready-чернетки
проходить ті самі перевірки; publish --force в обхід ledger не реалізується.

Якщо Telegram підтвердив відправку, але insert не вдався, наступна дія —
відновлення запису, не ще одна відправка. Повний/несправний диск до send
блокує надсилання, якщо не можна надійно зберегти payload/guard/майбутній receipt.

Редагування власного поста — окреме підтверджене виконання. У БД оновлюється
той самий message_id, за потреби з історією тільки власних опублікованих версій.
Видалення власником не означає дозволу автоматично опублікувати пост знову.

==============================================================================
15. ПОМИЛКИ, ВІДНОВЛЕННЯ ТА ПРОПУЩЕНІ ВИПУСКИ
==============================================================================

FloodWait: зберегти pause_until у /state, чекати щонайменше вказаний час.
Restart не скидає паузу. Ротація акаунтів/проксі для обходу не допускається. [Д13]
Мережеві збої — обмежений exponential backoff із jitter у межах активного job.
Auth failure — AUTH_REQUIRED, без циклу повторного login. Недоступний destination
блокує тільки його профіль, якщо немає спільної системної причини.

Часткова історія:
  min_complete_source_ratio=0.8 як початковий параметр;
  denominator — унікальні активні джерела snapshot;
  numerator — джерела із завершеним скануванням дозволеного діапазону;
  unavailable/excluded не видаються за complete; aliases не збільшують частку.
Будь-яку неповноту позначати. Required source неповний або частка нижча порогу
→ статусне зведення/ручний розгляд, а не удаваний повний огляд.
AI coverage обліковувати окремо від успішного читання історії.

Відновлення контейнера:
  1. Захопити process lock; перевірити published DB і службові JSON-файли.
  2. Перед усіма потенційними повторними sends розібрати receipt/uncertain guards.
  3. Відновити допустимий незавершений job із тимчасового кешу.
  4. Кеш втрачено, але send не починався → можна пересканувати ЙОГО вікно.
  5. Визначити належні misfires із розкладу/активації, не з останньої публікації.
Не сканувати всі джерела фоном лише через restart.

За замовчуванням запізнілий випуск допускається протягом 3 годин після cutoff,
із позначкою запізнення і незмінним [start,end). Профіль може перевизначити grace.
Якщо вийшов новіший пост профілю — старіший автоматично не публікувати.
Старий пропуск позначати skipped у /state; БД не отримує фіктивний пост.
Не видавати десятки catch-up випусків після тривалого простою.

Невдала AI-обробка → явний fallback або skip за конфігурацією. Непідтверджені
чернетки залишаються тільки в кеші до TTL. Після TTL видалити також prompts,
responses та raw; minimal delivery guard зберігається без цих текстів.

Несправний/переповнений кеш або state storage → не переносити контент у БД
як workaround. Publication hold, безпечне завершення активної спроби, alert.
Втрата/пошкодження state після backup restore → не припускати, що відправок
не було; перевірити destinations до відновлення публікації.

Alerts групувати, початково не частіше разу на тип помилки за 30 хвилин.
Виводити технічні statuses і локально: Telegram не може бути єдиним засобом
повідомлення про власну недоступність. Логи не містять новинних текстів.

17. ПРАВИЛА ВАЛІДАЦІЇ ТА ЗМІНИ КОНФІГУРАЦІЇ
==============================================================================

Безпечне читання YAML, перевірка типів, заборона unknown fields, duplicate keys,
небезпечних tags/eval і необмежених aliases. Regex не може блокувати worker:
обмежити складність/час. Safe loading і forbid extra fields документовані. [Д18, Д19]

Валідація:
  • унікальні profile/source IDs; refs підтримувані й закріплені за peer;
  • source_ids — УПОРЯДКОВАНИЙ список, не set; не сортувати при нормалізації;
  • повтори peer через aliases зводяться до найпершої позиції;
  • кожен активний профіль має дозволені джерела й власний destination;
  • жоден destination не є вхідним source; destinations профілів різні в MVP;
  • timezone валідна; daily_slots — непорожні унікальні HH:MM;
  • fixed_interval.every_seconds — ціле >=60, anchor_at має явний UTC offset;
  • trigger типізований; чужі поля іншого типу не успадковуються;
  • window тільки between_scheduled_boundaries, bounds=[start,end);
  • target/timeouts додатні, scan_target <= publication_target <= run_timeout;
  • дуже щільний розклад із довгим run_timeout — явне попередження про backlog;
  • cache TTL додатний і покриває погоджений горизонт активних retries;
    за default він не менший за max(run_timeout, misfire_grace) профілів;
  • max_cache_size додатний; cache/state/data — різні каталоги й не в репозиторії;
  • database_scope тільки confirmed_publications_only; allow_news_content=false;
  • realtime_ingestion=false, startup_scan=false, collection_mode=scheduled_history;
  • visible_links_per_item=1; source_selection=profile_source_order;
  • item_template має тільки summary і source_link; URL приходить із renderer;
  • display_name не порожній/не multi-line, якщо заданий; жодної URL-ін'єкції;
  • max_items/max_chars додатні, перевіряються runtime-ліміти Telegram;
  • selection_mode=important — чинний робочий контракт до уточнення власника;
  • ai_processing approved вимагає evidence_ref, scope, строк і провайдера;
  • read_basis: pending_review | legitimate_client_use | documented_permission;
  • republication: pending_review | allowed | blocked; AI: blocked | approved;
  • provider=openai, api_style=responses, початковий model=gpt-5.6-sol;
  • secret, тарифна таблиця, бюджети та параметри моделі налаштовані;
  • automatic_model_fallback=false; API доступ перевіряє явна ai-check;
  • published_retention покриває cross_window_memory і потрібний журнал доставки;
  • backups виключають cache і не створюють постійних копій raw.

TTL кешу відлічується від створення run, НЕ від дат постів у його вікні.
Для добового/довшого вікна не потрібен багатоденний фоновий збір: історія
читається на його межі. Потрібний обсяг кешу і час API залежать від обсягу історії.

Порядок звичайних defaults: built-in → global → profile → дозволені overrides.
Права — перетин обмежень, а не «останнє значення перемагає».
source_overrides можуть змінювати priority/required, але не послаблювати права
і не підміняти порядок source_ids для видимого посилання.

reload-config: перевірити candidate цілком, потім атомарно застосувати.
Зберегти не секретний snapshot/checksum у /state. Поганий новий YAML залишає
попередню версію чинною. Джерела, їхній ПОРЯДОК, формат, destination, AI-параметри
й розклад змінюються з наступної межі профілю. Відкликання прав/вимкнення — негайно.
Уже sending/sent payload не переформатовується через reload.

schedule.trigger замінюється цілком, times/source_ids — теж цілком, не merge.
Зміна порядку source_ids інвалідує attribution/render cache, навіть якщо набір
peer ID лишився той самий; додати source_order_hash до відповідних cache keys.
Порядок не є доказом достовірності й не скасовує перевірку claims.

Схема конфігурації цієї версії — 3 (номер документа — 4.0).
migrate-config 2→3: прибрати фоновий polling/startup backfill і raw/evidence
retention, додати scheduled_history, cache/state, format_defaults та нову
політику БД. Зберегти незалежні розклади/OpenAI/джерела й ЯВНО зберегти їхній порядок.
Міграція не робить платних API-викликів і не переписує оригінал без підтвердження.

Якщо реалізація старої схеми вже існує, міграція даних — окрема підтверджена
операція: перенести тільки достовірні sent-пости, технічний стан без контенту,
не переносити raw/candidates у нову БД. Перед видаленням старого архіву погодити
порядок очищення та наявні backups; не залишати його прихованою активною копією.
Саме це ТЗ не виконує жодної міграції сервера чи видалення даних власника.

18.1. Контентна SQLite-БД: тільки published_messages

Одна предметна таблиця published_messages; технічну версію схеми можна вести
через PRAGMA user_version, не через таблиці новин/запусків.

Пропоновані поля одного підтвердженого вихідного поста:
  publication_id; digest_key UNIQUE; profile_id;
  destination_peer_id; destination_message_id;
  window_start_utc; window_end_utc; scheduled_at_utc;
  published_at_utc; confirmed_at_utc; confirmation_method (ack|reconciled);
  rendered_text; entities_json; payload_hash; marker; random_id;
  config_version; schedule_revision; source_order_snapshot_json;
  items_json; coverage_summary_json; ai_usage_summary_json;
  metadata_recovery (complete|partial); own_edit_history_json (optional).
  UNIQUE(destination_peer_id, destination_message_id).
  UNIQUE(profile_id, window_start_utc, window_end_utc).

confirmation_method та конкретний Telegram message ID обов'язкові.
Немає статусів scheduled/processing/failed/uncertain у цій таблиці.
Текст, записаний тут, — фактично опублікований вихідний текст, не draft.
При recovery з неповними metadata відповідні поля nullable, без вигадування.

items_json містить ТІЛЬКИ пункти, що є у фінальному вихідному пості:
  position, власний short_summary, власні published_claims, event_fingerprint,
  is_update, displayed_source_id/peer/message_id/url/label,
  used_source_refs [{peer_id, message_id, url, optional version_hash}].
Без raw_text, normalized_text, evidence_fragments, повних prompts/responses,
невикористаних кандидатів або постів, які відкинули. References — мінімальні
metadata походження саме ОПУБЛІКОВАНОГО пункту, не база всіх сканованих повідомлень.

coverage_summary_json — агрегати (counts/statuses) випуску, не список raw.
ai_usage_summary_json — витрати/модель/usage цього опублікованого run;
невдалі runs не створюють рядки лише заради аналітики витрат.
Власні вже опубліковані редакції можна зберегти разом із їхнім confirmed edit time.

Не створювати постійних предметних таблиць messages, message_versions,
source_scan_ranges, runs, run_inputs, run_items, outbox, processing_cache,
profile_events або usage_ledger для неопублікованої роботи.
Нова таблиця з іншою назвою, що зберігає raw, також заборонена.

Індекси: profile_id+published_at, window_end_utc, destination_peer_id+message_id.
SQLite на локальному диску, контроль durability, WAL/busy timeout.
WAL не розміщувати на мережевій shared filesystem. [Д14]
Мережевий send не є частиною SQLite-транзакції. Після ack записати власний пост
атомарно; помилка commit не є дозволом повторити вже підтверджений send.

18.2. Тимчасові файлові дані

  /cache/runs/<digest_key>/manifest.json
    profile/window/config/source-order snapshot, coverage, cursor, created_at,
    expires_at, фаза роботи, safe error;
  /cache/runs/<digest_key>/messages.jsonl
    отримані вхідні повідомлення та спостережені версії;
  /cache/runs/<digest_key>/candidates.json, events.json
    тимчасові фільтри, злиття, claims/evidence;
  /cache/runs/<digest_key>/ai_result.json, outgoing.json, receipt.json
    чернетка/відповідь, готовий payload, тимчасове підтвердження;
  /cache/shared/<scan_batch>/<peer>/...
    спільні дані ТІЛЬКИ поточних паралельних споживачів.

Жодного SQLite raw-cache під іншим шляхом. JSON/JSONL також не стають архівом:
обов'язковий TTL, reference cleanup, hard size limit і виключення з backup.
Імена файлів конструюються з безпечного hash/ID, не з довільного channel title.

18.3. Мінімальні службові файли, не новинна БД

  /state/runtime.json:
    активація профілів, schedule revisions/cutover, матеріалізовані межі,
    skipped/paused metadata, pinned peer IDs і версії конфігурації без секретів;
  /state/delivery_guards.json:
    digest_key, destination, marker, payload_hash, random_id, фаза, час,
    за наявності підтверджений message_id; без текстів;
  /state/budgets.json:
    дата app.timezone, витрачені/зарезервовані суми, tokens, reservations,
    pending/uncertain request IDs; без prompts/responses/news;
  /state/rate_limits.json:
    pause_until і технічні квоти;
  /state/process.lock:
    взаємне виключення власника Telegram-сесії й writers.

Ці файли потрібні для розкладу, бюджету та захисту повторів при правилі
«БД тільки після публікації». Вони НЕ повинні містити копії новин, summaries
неопублікованих подій або snippets. Межі/статуси/хеші без контенту — дозволений
мінімальний технічний стан. Очищення /cache не знищує невизначені delivery guards.

Один writer під lock; оновлення через temporary file → flush/fsync → atomic
replace → sync директорії, де застосовно. Читати тільки цілі валідовані файли.
Version/checksum для виявлення пошкоджень. Не покладатися на просте write_text
у той самий файл під час одночасних writers або аварійного вимкнення.
Пошкоджений state → hold/recovery, не «почати з нуля й усе надіслати».

Метадані завершених guards можна компактно видаляти після звірки з чинною БД
та завершення погодженого горизонту. Unresolved guards — до ручного вирішення,
без збереження raw понад TTL. Після обрізання давнього ledger автоматичний
історичний replay за межами журналу заборонений.

20. БЕЗПЕКА, СЕКРЕТИ ТА ІЗОЛЯЦІЯ
==============================================================================

Секрети: api_hash, session, OpenAI API key, одноразові login-коди,
пароль 2FA та приватні invite links. Не публікувати їх у репозиторій,
Docker image, exception trace, metrics labels або зведення.

Docker Compose secrets монтує дозволені сервісу секрети як файли; використовувати
цей механізм для постійних API-реквізитів. Він не скасовує захист host-файлів
і не означає автоматичне шифрування диска. [Д16]

Session зберігати в окремому /session persistent volume з мінімальними правами.
Не передавати session-рядок через chat чи email. Для резервної копії сесії
передбачити окреме шифрування та доступ; за замовчуванням не включати її
в звичайний backup контентної БД.

Контейнер: non-root, read-only root filesystem, без privileged, без Docker
socket і без зайвих capabilities. Лише /data, /cache, /state, /session і потрібні tmpfs — writable.
Не відкривати порт назовні для адміністрування MVP.

Online CLI взаємодіє з worker через локальний Unix socket з перевіркою прав.
Він не відкриває другий Telegram-клієнт. Офлайн-команди, яким потрібна сесія,
вимагають зупинення worker і захоплення того самого process lock.

У LLM передавати лише дозволені новинні поля та мінімальний контекст.
Не передавати весь Telegram update, акаунтні metadata, список контактів або
зміст нерелевантних чатів. Логування повних prompts за замовчуванням вимкнене.

Зовнішні статті не завантажуються в MVP. Майбутній web/RSS-адаптер повинен мати
дозволений список доменів, ліміти розміру й часу, перевірку redirect/DNS,
блокування localhost, приватних IP, metadata endpoints, file:// та інших
непотрібних схем. Посилання з допису не є довіреною адресою для серверного HTTP.

Публікувати тільки у destinations із конфігурації. Навіть валідна відповідь
LLM не може підмінити канал призначення або ініціювати особисту розсилку.
Для вхідних каналів не змінювати повідомлення, не ставити реакції та не
маніпулювати лічильниками переглядів.

При витоку session: відкликати сесію через Telegram, зупинити worker,
перевірити публікації, авторизувати нову сесію і лише потім відновлювати роботу.

openai_api_key зберігати окремо від Telegram-реквізитів і монтувати тільки
сервісу app. Не просити пароль/браузерну сесію ChatGPT. Model ID не є секретом.
Перед ротацією ключа перевірити новий доступ без скидання розкладу або втрати активного run.
Відкликання ключа не повинно стирати чергу, coverage або журнал доставки.
Запити йдуть до зафіксованого OpenAI base_url; не підміняти його довільним URL
із новини або відповіддю моделі. Нестандартні сумісні проксі не входять до MVP.

/cache — такі самі чутливі дані, як новинні тексти до очищення; обмежити доступ
і за потреби шифрувати диск. TTL не означає гарантоване фізичне стирання секторів
SSD. Не створювати автоматичні host snapshots/backups кешу або crash dumps із raw.
Діагностика з контентом — лише явна погоджена операція, не прихована default-функція.
У /state дозволені тільки визначені metadata; секрети й новинні тексти заборонені.

==============================================================================
21. DOCKER-РОЗГОРТАННЯ ТА ПОСТІЙНІ ДАНІ
==============================================================================

Один Docker-сервіс app. Постійну БД власних публікацій, авторизаційну сесію
та мінімальний службовий стан відокремити від тимчасового cache volume.
Кеш може переживати restart для retry, але очищається за TTL/успіхом і не
входить у backup. Не монтувати весь /opt/newsdigest одним backup-джерелом без
виключення cache/session/secrets за політикою.

Приклад Compose-контракту; executable digest встановлюється Dockerfile:

----- BEGIN COMPOSE YAML -----
services:
  app:
    build: .
    image: local/newsdigest:0.1.0
    init: true
    user: "10001:10001"
    command: ["digest", "run", "--config", "/config/config.yml"]
    restart: unless-stopped
    read_only: true
    cap_drop: ["ALL"]
    security_opt:
      - "no-new-privileges:true"
    volumes:
      - ./config:/config:ro
      - ./data:/data
      - ./cache:/cache
      - ./state:/state
      - ./session:/session
    tmpfs:
      - /tmp:size=64m,mode=1777
      - /run/app:size=16m,uid=10001,gid=10001,mode=0700
    secrets:
      - telegram_api_id
      - telegram_api_hash
      - openai_api_key
    healthcheck:
      test: ["CMD", "digest", "healthcheck", "--socket", "/run/app/control.sock"]
      interval: 60s
      timeout: 5s
      retries: 3
      start_period: 60s
    stop_grace_period: 60s
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"

secrets:
  telegram_api_id:
    file: ./secrets/telegram_api_id
  telegram_api_hash:
    file: ./secrets/telegram_api_hash
  openai_api_key:
    file: ./secrets/openai_api_key
----- END COMPOSE YAML -----

До запуску підготувати directories й permissions: UID 10001 читає config/secrets,
пише тільки в потрібні томи. Немає chmod 777, root/privileged або Docker socket.
API-ключі — secret files; Compose secrets не замінюють захист host/disks. [Д16]
Жодних публічних портів і bot token.

Час сервера синхронізований; в образі актуальна timezone database.
Моменти зберігаються в UTC, розклади — за timezone конкретного профілю.
Глобальна TZ контейнера не змінює бізнес-правила.

SIGTERM: зупинити створення нових runs, записати активний cache/state, завершити
або позначити невизначений send, від'єднати клієнт і закрити SQLite.
Після kill -9 відновлення йде через файли/confirmed DB, не через припущення про успіх.
Після idle shutdown клієнта наступний належний run повторно використовує сесію.

Healthcheck не сканує історію, не генерує AI-відповідь і не вважає idle-клієнт
несправним. Для завислого процесу потрібен watchdog/зовнішній контроль;
не перезапускати контейнер циклічно через штатний FloodWait або очікування слоту.

22. CLI ТА ПОРЯДОК ПЕРШОГО ЗАПУСКУ
==============================================================================

CLI-контракти:

  digest validate-config --config /config/config.yml
    Локальна валідація, без збору новин, платних викликів і публікації.
  digest login --config /config/config.yml
    Інтерактивний login, worker зупинений, спільний session lock.
  digest dialogs
    Канали, ID, типи й права. Не завантажує новинну історію.
  digest doctor
    Перевірка прав/ID/конфігурації, каталогів, budget/state/DB, без source scan.
  digest schedule --profile crypto --next 10
    Майбутні межі/вікна/revisions; --all для всіх профілів.
  digest schedule-diff --config /config/config.yml
    Перехід old→new, affected profiles, без застосування.
  digest ai-check
    Доступ до моделі; --probe — явний синтетичний платний тест у межах бюджету.
  digest migrate-config --from /config/config-v2.yml --to /config/config-v3.yml
    Міграція schema_version 2→3 (не номерів ТЗ), без server/data мутацій.
  digest status
    Наступні запуски, активні cache manifests, guards, confirmed publications.
  digest preview --profile ukraine --window-end 2026-11-10T08:00:00+02:00
    Явне ручне сканування потрібного вікна, формування без відправки/insert у БД.
    Показати також вибране source_id/message_id й позицію у source_ids.
  digest publish --run-id <cached-ready-run-id> --confirm
    Надсилання наявного валідного payload через delivery guard.
  digest reconcile --profile ukraine
    Перевірка невизначених надсилань у ВЛАСНОМУ каналі без сканування джерел.
  digest cache-status
    Обсяг, активні споживачі, вік/TTL; не друкувати новинні тексти.
  digest cache-clean --expired-only
    Очистити прострочений/звільнений кеш без видалення unresolved guards.
  digest reload-config
    Валідація/атомарне застосування з наступної межі; права — негайно.
  digest backup
    Узгоджена БД публікацій + мінімальний state/config; БЕЗ кешу.
  digest healthcheck --socket /run/app/control.sock
    Локальний heartbeat, без source history requests і платних AI-викликів.

Online-команди делегують Telegram-операції єдиному worker через Unix socket.
Offline-команди захоплюють той самий lock і не працюють паралельно із worker.

Перший запуск:
  1. Заповнити refs, упорядковані source_ids, destinations, права, secrets і budget.
  2. Підготувати config/data/cache/state/session directories та permissions.
  3. docker compose build; validate-config через одноразовий контейнер.
  4. docker compose run --rm app digest login --config /config/config.yml.
  5. docker compose up -d у mode=preview; перевірити IDs через doctor/dialogs.
  6. ai-check, явний --probe і schedule --all.
  7. Дочекатися preview за розкладом або явно викликати ручний preview.
  8. Перевірити текст/посилання/порядок, порожню БД після preview й очищення кешу.
  9. Переключити production через reload-config, перевірити першу публікацію.
 10. Перевірити: insert тільки після доставки, raw відсутній у БД, cache очищений.

Запуск сервісу й підписка акаунта самі по собі не починають безперервний збір.
В OPERATIONS описати missing cache, uncertain send, state corruption, restore,
quota/FloodWait, заповнений диск і ручне рішення без небезпечного publish --force.

==============================================================================
23. СПОСТЕРЕЖУВАНІСТЬ, ЗБЕРІГАННЯ ТА BACKUP
==============================================================================

Структуровані логи: timestamp, level, component, profile_id, digest_key,
duration_ms, error_code, counts. Без текстів новин, повних приватних URL,
prompts/responses, session, ключів або login-кодів.

Метрики:
  heartbeat, очікування наступного слоту, active jobs;
  час початку сканування/його тривалість/кількість сторінок і дописів;
  coverage за run; причини виключень агрегатами;
  кеш: bytes, run count, max age, TTL deletions, active references;
  attribution: first-source selections, fallback через недоступність;
  OpenAI: latency/tokens/cost estimates/errors, numeric reservations;
  send/reconciliation errors, unresolved guards, час останньої публікації;
  вільний диск, DB/state backup age, schedule revisions і misfires.

Readiness враховує idle: відсутність з'єднання Telegram між jobs не є аварією.
Відсутність news scan між слотами — очікуваний стан, не collection lag.
Метрики не створюють новинної БД для неопублікованих подій.

Початкові строки:
  вхідні raw/нормалізовані тексти/evidence/AI draft — до завершення run,
    для retry максимум TTL 24 години; shared refs не подовжують TTL безмежно;
  власні підтверджені вихідні пости й їхні metadata — 365 днів;
  логічна пам'ять для змістових повторів — останні 7 днів власних постів;
  completed delivery guards — погоджений горизонт/звірка з БД;
  unresolved guards — до вирішення, тільки безконтентні metadata;
  backups — 7 днів за default.

Кеш НЕ входить у backup, контейнерний image, diagnostic dump або архів fixture.
Окремий export preview з текстом можливий лише за явним запитом власника,
з конкретним призначенням/строком; це не default-поведінка застосунку.
Відкликання дозволів негайно припиняє обробку й очищає відповідний тимчасовий
контент; для вже опублікованих матеріалів — review/погоджена корекція.

Backup SQLite через узгоджений backup API, а не копіювання одного main-файлу
під час активного WAL. Механізм описаний SQLite/Python. [Д14, Д15]
Узгоджений backup-комплект: published.sqlite3, мінімальний /state, не секретні
config snapshots. Для узгодженості на короткий час зупинити нові send/state
mutations під lock, зафіксувати manifest/time/checksum; мережевих sends у цей
момент не повинно бути. Сесія — окремо зашифрована політика, не звичайний backup.

Після restore старої БД/старого state:
  publication hold → звірити власні канали за markers → відновити confirmed
  пости, що вже вийшли після backup → узгодити guards → відновити розклад.
Не покладатися тільки на «порожній cache». Вхідний кеш назад не відновлюється;
для ще допустимого, не надісланого вікна допускається нове scheduled-job scan.

Старий budget snapshot може недооцінювати витрати. До нових платних викликів
узгодити API-витрати/встановити консервативний резерв або дочекатися нового
бюджетного періоду; не обнуляти ledger counters мовчки.
Backup поза основним диском, зашифрований, restore перевірений. Після очищення
кешу повний аудит історичних raw неможливий — зберігаються тільки власні пости
і мінімальні references фактично використаних джерел.

==============================================================================
24. ПРОДУКТИВНІСТЬ, РЕСУРСИ ТА КОНТРОЛЬ ВИТРАТ
==============================================================================

Початковий орієнтир для планування: 2 vCPU, 2 GB RAM, 10 GB SSD; зовнішній
OpenAI API, без локальної LLM/GPU. Це оцінка, не вимір продуктивності.

Контрольні сценарії: 50 джерел, 5 профілів, до 10 000 вхідних текстових постів
за добу; одночасні й різні daily_slots та fixed_interval. Оскільки сканування
починається на cutoff, хвиля getHistory/API-навантаження приходиться на слот.
180 секунд від cutoff до поста — ціль, яку потрібно підтвердити на стенді,
а не гарантія; не реалізовувати прихований фоновий збір заради цього SLO.

Орієнтири: due-job створюється протягом 10 секунд; input scan має target 60
секунд, загальний target 180, активна спроба timeout 600. Фактична тривалість
залежить від постів/пагінації/FloodWait/AI-черги. За нестачі ресурсів показувати
partial/late, а не читати перші 100 повідомлень і заявляти повноту.

Оптимізації без порушення вимог:
  • об'єднання однакових source scans тільки для одночасних активних runs;
  • локальне прибирання точних повторів до AI;
  • мінімальна пам'ять із власних опублікованих пунктів;
  • повторне використання валідованого результату лише в межах активного кешу;
  • обмежені repair/retry й контроль response tokens.
Кеш завершеного випуску не зберігати довго «задля економії».

Бюджети: per_digest, per_profile_day, global_day. Дата всіх денних бюджетів —
app.timezone, незалежно від timezone профілів. Резервувати очікуваний максимум
атомарно у /state/budgets.json під lock ДО запиту. Паралельні профілі не можуть
разом перевищити глобальну межу через гонку. Preview/probe/repair враховуються.
Після відповіді врегулювати резерв за usage, після timeout — uncertain, не нуль.

Вартість OpenAI обчислювати за actual usage і перевіреним price_table_file:
розділяти неперекривні input/cached input/cache-write/output категорії та
контекстні пороги, що застосовні до поточного API/моделі. Тарифи не фіксувати
в коді або цьому ТЗ як незмінні. [Д28]
reasoning_tokens — деталізація, не додаткове нарахування поверх output total;
за неповних даних сума estimate/unknown. Тестувати відображення usage саме
поточної версії SDK/Responses, а не підставляти неіснуючі поля.

Контентна БД не використовується для failed/preview usage ledger: numeric
сумарні counters/reservations і технічні request IDs — у службовому стані.
Для підтвердженої публікації її usage summary можна записати в той самий рядок.
Зміна моделі/розкладу/порядку джерел/формату може потребувати нової оцінки витрат,
але не обнуляє вже витрачені суми.

==============================================================================
25. ОБОВ’ЯЗКОВІ ТЕСТИ
==============================================================================

Тести відтворювані на синтетичних або належно дозволених матеріалах.
Зовнішні інтеграційні перевірки — в тестових каналах власника, без spam.

Часові вікна й незалежні розклади:
  T01. 07:59:59, 08:00:00, 20:59:59, 21:00:00 потрапляють у правильні [start,end).
  T02. ukraine 08:00/21:00 та crypto 09:00/15:00/23:00 мають різні незалежні вікна.
  T03. Один слот на добу та fixed_interval 21600 із anchor працюють після restart.
  T04. DST: неоднозначний/відсутній час і колізії перенесених слотів не дають дубля.
  T05. Різні timezone й перехід дати/місяця/року не змішують межі профілів.
  T06. Перехід розкладу створює [C,N), без пропусків/перетинів; старий snapshot
       незмінний.
  T07. Зміна global defaults не перезаписує власні overrides інших профілів.
  T08. Пропущений випуск не розширює наступне вікно до часу last_sent_at.
  T09. Повторний reload до cutover замінює тільки pending revision із аудитом.
  T10. Після disable/enable не виникає лавини історичних випусків.

Сканування тільки за розкладом:
  T11. Між належними runs немає source getHistory-запитів або накопичення updates.
  T12. Перший запуск, login, doctor, dialogs і healthcheck не запускають source scan.
  T13. О 08:00 починається scan визначеного вікна; дані від 08:00 не включаються.
  T14. Перезапуск о 08:12 відновлює дозволений випуск із cutoff 08:00, не 08:12.
  T15. Понад 100 постів у вікні збираються пагінацією до start, без тихого обрізання.
  T16. Crash між cache write і cursor update не губить сторінку й не подвоює записи.
  T17. Shared source одного due batch читається спільно; coverage профілів незалежний.
  T18. Різні майбутні слоти не затримують поточний run заради об’єднання сканувань.
  T19. Видалення до першого scan не видається за відновлений матеріал; coverage
       пояснений.
  T20. Редакція edit_date>=cutoff без попередньої кешованої версії
       виключається/позначається.
  T21. Альбом не переносить пізні підписи через cutoff; media_only і URL-only не
       вигадуються.
  T22. Недоступність/порожній канал/незавершена пагінація мають різні coverage statuses.

Кеш і сувора межа контентної БД:
  T23. Повний scan, AI-обробка й ready-чернетка ще НЕ створюють рядків
       published_messages.
  T24. Успішний preview очищає cache, не записує БД і не змінює published-memory.
  T25. Підтверджений send створює один рядок тільки з реально опублікованими пунктами.
  T26. У БД/backup немає raw_text, normalized_text, evidence цитат або непублікованих
       candidates.
  T27. Після ack і DB commit run-cache очищається; shared cache чекає тільки активних
       consumers.
  T28. Невдалий job має bounded TTL; читання кешу не подовжує його безмежно.
  T29. TTL expiry зупиняє active job, видаляє контент і не видаляє uncertain guard.
  T30. Cache survives звичайний restart; cache loss до send допускає лише контрольований
       rescan вікна.
  T31. Cache full не видаляє активний матеріал мовчки й не записує його до БД як
       workaround.
  T32. В /state немає raw, prompts, responses або summaries неопублікованих подій.
  T33. Файли cache не входять до backup, image, стандартних логів і fixtures.
  T34. Пам’ять між випусками походить тільки з фактично опублікованих items_json.

Формат, посилання й групування:
  T35. Кожен новинний пункт має summary — channel label, один source-link, без голого
       URL.
  T36. Клік по назві відкриває конкретний використаний допис, не головну сторінку
       каналу.
  T37. Серед source_ids=[A,B,C] і учасників=[B,C] вибирається B, не A і не C.
  T38. Серед учасників=[A,B] вибирається A навіть за пізнішого поста й нижчого priority.
  T39. Порядок глобального sources mapping/алфавіт/відповідь LLM не змінюють вибір.
  T40. Одна подія в різних профілях може мати різний видимий канал за їхніми source_ids.
  T41. Кілька постів одного каналу дають latest_relevant із потрібного вікна та події.
  T42. Reload порядку не змінює відкритий snapshot; для нового вікна інвалідує render
       cache.
  T43. Aliases одного peer зберігають найранішу позицію, не створюють зайвого джерела.
  T44. Недоступний anchor перед send переобирається детерміновано; після sending payload
       незмінний.
  T45. Назви з emoji, &, <, дужками й кирилицею не ламають offsets/entities та не
       додають URL.
  T46. Десять копій дають один пункт; кілька перевірених provenance refs не стають
       кількома видимими links.
  T47. Істотні деталі іншого каналу атрибутуються або виключаються, не приписуються
       видимому каналу.
  T48. Різні події про один актив/місто не зливаються; числа/заперечення не губляться.
  T49. Стара опублікована подія без розвитку пропускається, новий факт/спростування
       з’являється.
  T50. Завеликий текст скорочується до одного поста без втрати посилань, фактів або
       заперечення.

OpenAI й захист контенту:
  T51. AI stages використовують model snapshot gpt-5.6-sol; немає прихованого model
       fallback.
  T52. Blocked/private/protected текст не потрапляє у заборонений AI/export шлях.
  T53. Відкликання прав блокує ще не відправлені матеріали й очищає відповідний кеш.
  T54. Prompt injection не отримує секретів, не змінює destination/source order і не
       виконує команд.
  T55. Невідомі refs, неіснуючі evidence, invalid JSON, refusal/incomplete не
       публікуються.
  T56. 429 rate limit і quota помилки мають різні retry-політики в одному загальному
       ліміті.
  T57. Preview/probe/repair враховані в бюджеті; дві паралельні reservations не обходять
       global cap.
  T58. Невідомі витрати після timeout не стають нульовими; input/cache/reasoning не
       рахуються двічі.
  T59. store=false, tools відсутні; локальний AI-кеш очищується, secrets відсутні в
       payload/logs.
  T60. Rule_based fallback позначений і також має один лінк/той самий source-order
       алгоритм.

Доставка, збої й відновлення:
  T61. Два конкурентні jobs одного key не проходять guard для двох sends.
  T62. Crash до send не записує false publication; той самий payload має збережений
       random_id.
  T63. Telegram ack передує insert; crash після ack відновлює запис, а не повторює
       публікацію.
  T64. Втрачена відповідь переводить guard у uncertain, без рядка «можливо» в БД.
  T65. Reconciliation знайденого own post вставляє confirmed record із реальним
       message_id.
  T66. Відсутність серед останніх N повідомлень не трактують як доказ недоставки.
  T67. TTL/cache loss після sending не дозволяє повторно згенерувати й надіслати інший
       текст.
  T68. Часткове metadata recovery не вигадує старих source refs, AI usage або evidence.
  T69. Помилка DB commit після доставки не спричиняє повторного send.
  T70. Зміна destination username на інший peer блокує публікацію, не перемикає канал
       мовчки.
  T71. Новіший пост профілю блокує автоматичний вихід старішого misfire.
  T72. Повний цикл backup→restore→own-channel reconciliation не повторює вже надіслані
       пости.

Експлуатація й приймання:
  T73. Невалідний YAML/reload залишає чинну конфігурацію; source_ids не сортується.
  T74. Atomic state write після crash дає старий або новий валідний файл, не мовчазний
       reset.
  T75. FloodWait pause_until переживає restart; очікування не вважається приводом для
       обходу.
  T76. Заповнений диск/state corruption блокують небезпечні sends і дають alert.
  T77. Cache/data/state/session volumes та backup exclusions відповідають ТЗ.
  T78. Міграція schema 2→3 не переносить raw у нову БД й не починає платні запити.
  T79. Після restore budget counters не скидаються до нуля для нових AI-викликів.
  T80. Секретів/новинних текстів немає у звичайних log/metrics/error dumps.
  T81. Нульові новини, неповне сканування і AI-помилка розрізняються у вихідних
       статусах.

26. КРИТЕРІЇ ПРИЙМАННЯ
==============================================================================

Функціональні критерії:
  A01. Один звичайний акаунт, різні списки/destinations, без BotFather.
  A02. Третій профіль і незалежний розклад додаються через YAML без правок коду.
  A03. На належну межу — один випуск за її [start,end), не потік перепостів.
  A04. Сканування починається тільки за розкладом/явним preview/контрольованим retry;
       мережевий тест підтверджує відсутність фонового читання джерел.
  A05. До підтвердження send БД не отримує рядок; preview/failed — теж без insert.
  A06. У БД тільки власні підтверджені пости та metadata опублікованого змісту;
       жодного прихованого raw-архіву в таблицях, JSON-полях, state чи backups.
  A07. Кеш успішного run очищений; failed bounded TTL; unresolved guard без контенту.
  A08. Кожний новинний пункт має «короткий зміст — клікабельна назва каналу».
  A09. Для merged event рівно один лінк на допис першого eligible source_ids каналу.
  A10. Порядок незалежний від priority і часу, зафіксований у snapshot і протестований.
  A11. Семантичні повтори між випусками перевіряються за власними публікаціями БД.
  A12. OpenAI Responses / gpt-5.6-sol — основний AI-прохід, не прихована інша модель.
  A13. Права, factual grounding, бюджети й destination не залежать від волі LLM.
  A14. Втрата cache/відповіді/DB commit не спричиняє сліпого повторного send.
  A15. Відновлення backup, schedule transition і cache TTL перевірені зі збоями.
  A16. Усі обов'язкові тести T01–T81 проходять.

Якість на контрольному корпусі:
  не менше 200 дозволених/синтетичних повідомлень і 50 розмічених подій;
  точні повтори усуваються в усіх тестах;
  AI semantic merge: початкова ціль precision >=95%, recall >=85% на погодженому
  корпусі за явно визначеною парною/кластерною метрикою;
  кожний source-link походить від реального eligible message record;
  немає непідтверджених доданих фактів або змінених чисел/заперечень;
  додаткові факти не приписуються першому каналу лише через видимий лінк.
Це критерії тестування, не гарантія нульової помилки на майбутніх новинах.
Rule_based не вважається виконанням семантичних метрик AI-режиму.

Експлуатація:
  7 днів стендового прогону різних розкладів;
  виміряні scan/runtime/coverage/cache metrics і ціль затримки 180 секунд;
  працездатний backup/restore без кешу, опис AUTH_REQUIRED/uncertain/state corruption;
  передані код, lockfile, config.example.yml, Compose, тести, README, OPERATIONS
  і звіт перевірки. README окремо пояснює, що idle не означає несправність.

==============================================================================
27. ЕТАПИ РЕАЛІЗАЦІЇ ТА МЕЖІ ПЕРШОЇ ВЕРСІЇ
==============================================================================

Етап 1 — конфігурація, session, моделі зберігання.
Упорядковані sources/profiles, права, login/doctor, minimal confirmed-only DB,
atomic service state, тимчасовий cache manager, Docker/permissions/preview.

Етап 2 — розклади та сканування.
Незалежні daily_slots/fixed_interval, вікна, міграція розкладу, paginated scan
тільки на cutoff, shared active-batch cache, partial coverage, TTL/resume.
Жодного always-on collector як проміжної production-архітектури.

Етап 3 — обробка й формат.
Фільтри/дедуплікація, rule_based перевірка, attribution за порядком конфіга,
один пункт/один прихований лінк, renderer/entities, перевірка довжини.

Етап 4 — OpenAI.
GPT-5.6 Sol через Responses, strict schema, facts/evidence у кеші,
міжвипускна пам'ять із published messages, budgets/retries/fallback,
перевірка якості та захисту від injection.

Етап 5 — доставка і confirmed insert.
Файловий temporary payload, durable minimal guard, send/ack/reconciliation,
insert тільки після підтвердження, cleanup cache, recovery/backup/fault injection.

Етап 6 — тестова експлуатація.
Різні розклади, TTL/overflow/late edit, довгі вікна, shared sources, preview
і production у тестових каналах; перевірка відсутності raw у БД/backup/state.
Після 7-денного прогону — контрольований запуск.

Не входить у MVP:
  вебпанель/мультитенантність/кілька акаунтів;
  архів вхідних постів або історії їхніх редакцій;
  фоновий ingestion, незалежне періодичне опитування джерел;
  інші AI-провайдери, локальна LLM, непогоджена підміна моделі;
  cron/calendar exceptions/перекривні lookback-вікна;
  OCR, транскрипція, медіафайли, довільний web crawling;
  автоматичний join, обхід приватності/лімітів/захисту/прав;
  торгові сигнали, угоди або гарантія достовірності Telegram-повідомлень;
  позапланові breaking-news пости.

Майбутні розширення: дозволені RSS/API, UI конфігурації, ручне погодження,
окремий bot-публікатор. Вони не є прихованими залежностями чинної версії.

==============================================================================
28. ЩО ПОТРІБНО ДЛЯ ЗАПУСКУ І ЩО ЩЕ НЕ ВИЗНАЧЕНО
==============================================================================

Підтверджено власником:
  окремий звичайний акаунт; списки каналів через config; різні destinations;
  незалежні часові інтервали; OpenAI API / GPT-5.6 Sol;
  коротка новина — приховане посилання під назвою каналу;
  для злитої події — перший канал у списку конфіга серед учасників;
  сканування за розкладом, тимчасовий кеш вхідних постів;
  у БД — лише опубліковані власні повідомлення.

Прийняті технічні defaults, НЕ додаткові побажання користувача:
  файловий кеш, що переживає restart; max TTL 24 години і 512 MB;
  очищення успішного run після insert; без cache backups;
  мінімальні безконтентні /state-файли для розкладу/guards/бюджету;
  1–2 речення, numbered items, одна клікабельна назва після тире;
  якщо канал має кілька постів події — latest_relevant;
  display_name або Telegram title; URL — на допис, не на канал;
  важливі новини, до 8/6 пунктів; один вихідний пост, max_chars=3500;
  own publications 365 днів, логічна пам'ять 7 днів;
  08:00/21:00 як шаблон, Europe/Kyiv, target 180 секунд, run timeout 600;
  cutoff scan без prefetch; catch-up до 3 годин; AI reasoning=medium;
  права/приватний експорт перевіряються; спочатку mode=preview.

ОДНЕ ЗМІСТОВЕ УТОЧНЕННЯ ДО ВЛАСНИКА:
  «Коротка зведена інформація кожного поста» означає ВСІ унікальні новини
  за період (без реклами/дублів) чи лише відібрані головні новини?
  До відповіді збережено попередній відбір головного і робочі max_items=8/6.
  Не змінювати мовчки вимогу одного вихідного повідомлення: безмежний перелік
  усіх новин може не вміститись; остаточну overflow-політику погодити, якщо
  власник обере повне охоплення всіх унікальних постів.

Для production потрібні: остаточні refs/порядок джерел, destinations і права,
Telegram API credentials/login, OpenAI key із доступом до обраної моделі,
бюджети/перевірені тарифи, дозволи контенту, розклади й ресурси сервера.
09:00/15:00/23:00 для crypto у шаблоні — демонстрація, не погоджений розклад.

Відомий компроміс нової архітектури: немає повної історії видалених до scan
постів/редакцій і немає повного raw-аудиту після очищення кешу. Натомість
вхідні новини не накопичуються постійно, а БД містить тільки власні публікації.
Втрата кешу не скасовує захист повторів: його мінімальні metadata залишаються
у /state до узгодження, не у контентній БД і не як прихований архів новин.
